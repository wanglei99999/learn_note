# 工具调用：协议、设计与 MCP

创建日期：2026-10-17

[上一篇](01-一次API调用.md)的结尾，我们把一次调用的局限列成了一张表，前三行可以归成一句话：模型只能说，不能做。它不知道今天的天气，没法改你磁盘上的文件，数一篇文章里有几个“的”也数不准。

这一篇给模型一个能“做事”的接口：工具调用（tool use，OpenAI 叫 function calling）。先看协议是怎么一来一回的，再看工具该怎么设计，最后看两种特别的工具（Bash 和 computer use），以及把工具标准化的 MCP。

## 1. 工具调用的往返

### 1.1 工具定义

调用方在请求里多传一个 `tools` 字段，告诉模型有哪些工具可用。每个工具有三样东西：名字、一段说明、一个参数的 JSON Schema。

```text
tools = [
  {
    name: "get_weather",
    description: "查询某个城市当前的天气。只支持中国大陆的城市。",
    input_schema: {
      type: "object",
      properties: { city: {type: "string", description: "城市名，如“上海”"} },
      required: ["city"]
    }
  }
]
```

### 1.2 一来一回

用户问“上海现在天气怎么样”，整个过程是这样的：

![一次工具调用的往返](assets/tools/01-round-trip.png)

模型收到问题和工具列表后，判断自己答不了，需要查天气。于是它不输出普通文本，而是输出一个 `tool_use` 块：要调用哪个工具，参数是什么，再加一个 id。这次调用到此结束，`stop_reason` 是 `tool_use`。

你的程序拿到这个块，解析出参数，真正去请求天气服务，拿到结果。然后把整段历史，加上一条 `tool_result` 消息（用 id 对上是哪一次调用的结果），再发给模型。模型读到结果，写出最终回答。

写成伪代码：

```text
r1 = model.call(messages, tools)
if r1.stop_reason == "tool_use":
    call   = r1.tool_use
    result = execute(call.name, call.input)           # 你的代码在执行
    messages.append({role: "assistant", content: r1.content})
    messages.append({role: "user", content: [tool_result(call.id, result)]})
    r2 = model.call(messages, tools)                  # 第二次调用
```

有两点要看清楚。

第一，模型自始至终没有碰过天气服务。它做的事情只有一件：写出一段格式正确的文本，表达“我想调用 get_weather，参数是上海”。真正发请求的是你的程序。这意味着执行什么、拦不拦、出错了怎么处理，全部由调用方决定。第 11 篇讲权限和沙箱，都是在这一步上做文章。

第二，一次工具调用至少是两次 API 调用。上一篇讲过 API 是无状态的，所以第二次调用要把第一次的全部内容连同工具结果再发一遍。

### 1.3 序列里的工具调用

在模型眼里，工具定义、工具调用和工具结果都只是序列里的文本。工具定义被模板渲染进 system prompt 一类的位置；模型输出的 `tool_use` 是一段夹在特殊标记之间的 JSON；工具结果作为一条单独的消息拼回来。[SFT 与 Chat 模板](../深度学习/大模型训练/02-SFT与Chat模板.md)第 5 节画过这个序列的样子。

所以模型调用工具的能力，也是训练出来的：后训练数据里有大量示范，教它什么时候该调用、参数怎么按 schema 填。这带来几个直接的后果。

- 工具定义要占上下文。每个工具的名字、说明、schema 都会变成 token，每次调用都要发。工具一多，还没开始干活，上下文就被吃掉一大块。第 06 篇专门讲这个问题。
- 参数可能填错。模型可能少填一个必填字段，或者把数字写成字符串。上一篇讲的约束解码也可以用在这里，Anthropic 和 OpenAI 的接口都支持给工具打开严格模式，按 schema 约束参数的生成。
- 模型可能在不该调用的时候调用，或者该调用的时候硬答。接口一般提供 `tool_choice` 参数：让模型自己决定、必须调用某个工具、必须调用任意一个、或者禁止调用。

### 1.4 并行调用

如果一个问题需要查三个城市的天气，模型可以在一次响应里输出三个 `tool_use` 块。调用方可以并发执行这三个调用，把三个结果放在同一条消息里发回去。这样省掉了两次往返，也少了两遍全量重发。

前提是这几个调用互相独立。如果第二个调用的参数要从第一个调用的结果里来，比如先搜索文件、再读搜到的文件，那就只能一个一个来。

## 2. 工具设计

协议本身很简单，难在工具怎么设计。Anthropic 在 2025 年 9 月发过一篇《Writing effective tools for agents》，下面的很多例子出自这篇文章。

这篇文章开头有一个说法：传统的 API 是确定性系统之间的契约，同样的输入永远得到同样的输出；工具是确定性系统和一个不确定的 agent 之间的契约。agent 可能调用错工具，可能填错参数，可能完全没想到要用某个工具。所以给 agent 设计工具，和给程序员设计 API，是两件不一样的事。

### 2.1 不要把 API 原样包一层

最常见的做法是把现成的 API 一个个包成工具：有 `list_users` 就做一个 `list_users` 工具，有 `list_events` 就做一个 `list_events` 工具。这样做省事，效果往往不好。

原因在于程序和 agent 读数据的方式不同。程序遍历一万条联系人几乎不花时间；agent 每读一条都要花 token，而且上下文是有限的。Anthropic 的例子是：与其给一个返回所有联系人的 `list_contacts`，不如给一个 `search_contacts`，让 agent 直接按名字查。

同样的道理，几个总是连着用的操作，可以合并成一个工具。约一个会议，原本要先列出参会人、再查每个人的日程、再找空档、再创建事件，可以合并成一个 `schedule_event`，内部完成找空档和创建两步。查日志用 `search_logs`，只返回相关的行，而不是 `read_logs` 把整个日志倒出来。查客户信息用一个 `get_customer_context`，把客户资料、最近交易和备注一次性汇总，而不是让 agent 分别调三个工具再自己拼。

判断的标准是：一个人类员工拿到这个工具，会不会觉得顺手。人不会为了约个会把公司所有人的日程翻一遍。

### 2.2 命名空间

工具多了以后，名字容易撞，功能也容易混。一个 agent 同时接了 Asana 和 Jira，两边都有“搜索”，叫 `search` 就分不清了。

做法是加前缀：`asana_search`、`jira_search`；再细一点，`asana_projects_search`、`asana_users_search`。Anthropic 在文章里提到，前缀还是后缀对评估结果有影响，而且不同模型的偏好不一样，最好自己测一下。

### 2.3 返回值

工具返回什么，直接决定 agent 下一步能做什么。

**返回有意义的信息。** agent 处理自然语言的名字、标题比处理一串 UUID 可靠得多。返回 `{"assignee": "张三"}` 比返回 `{"assignee_id": "a7f3c9e2-..."}` 更不容易出错。只有在后续调用确实需要 id 的时候，才把 id 带上。

**让 agent 选择详细程度。** Anthropic 的做法是给工具加一个 `response_format` 参数，取值 `concise` 或 `detailed`。他们用 Slack 的一个例子测过：同一条消息线程，详细格式返回 206 个 token，带着 `thread_ts`、`channel_id` 这些后续操作需要的 id；精简格式只有 72 个 token，大约三分之一。agent 只是想看看讨论内容时用精简版，要回复某条消息时再用详细版。

**分页、过滤、截断。** 任何可能返回大量数据的工具，都要有分页或过滤参数，并且设一个合理的默认上限。Claude Code 默认把单次工具返回限制在 25,000 token。截断的时候，要告诉 agent 内容被截断了，以及怎么拿到它要的部分，比如“结果共 3,200 条，只显示前 50 条，可以用 `query` 参数缩小范围”。

### 2.4 错误信息

工具出错时返回的信息，是给 agent 看的，要能告诉它下一步怎么做。

返回 `Error 400` 或者一段 Python traceback，agent 只能猜。返回“`date` 参数格式错误：需要 YYYY-MM-DD，收到的是 ‘下周三’。请先换算成具体日期”，agent 下一轮就能改对。

这件事看着小，其实是 agent 能不能自己从错误里恢复的关键。第 03 篇讲循环的时候还会回到这里。

### 2.5 描述

工具的说明和参数说明，是模型决定调不调用、怎么调用的全部依据。Anthropic 的建议是：写得像给一个刚入职的同事解释这个工具。那些你觉得理所当然、所以没写下来的东西，比如某个查询用什么格式、某个术语指什么、几个资源之间是什么关系，新同事不知道，模型也不知道。参数名也要直白，用 `user_id` 而不是 `user`。

描述改得好不好，效果差别很大。Anthropic 提到，他们在 SWE-bench Verified 上测 Claude 3.5 Sonnet 时，对工具描述做了一些精确的修改，错误率大幅下降，最后拿到了当时的最好成绩。文章里还有一个小例子：Claude 在调用网页搜索工具时，总是在 `query` 后面画蛇添足地加上“2025”，把搜索结果带偏了，改了工具描述以后这个问题就没有了。

文章的标题后半句是“with agents”：他们的做法是让 Claude 自己读评估运行的记录，找出工具哪里让它困惑，再改写工具的描述和实现。在 Slack 和 Asana 两个内部工具集的留出测试集上，Claude 改过的版本比人写的版本表现更好。

## 3. 通用工具：Bash 与代码执行

前面讲的都是功能专一的工具：查天气、查联系人、约会议。还有一类工具反其道而行之，只给一个，但什么都能干。

最典型的就是 Bash。给 agent 一个能执行 shell 命令的工具，它就能用 `ls` 看目录，用 `grep` 搜代码，用 `cat` 读文件，用 `git` 看历史，用 `curl` 访问网络，用 `python` 跑一段脚本。这些命令行工具在预训练语料里出现了无数次，模型早就会用，不需要你一个个写工具定义。

代码执行是同一个思路。上一篇说模型数不准一篇文章里有几个“的”，这件事交给一行 Python 就解决了。很多“模型不擅长”的事，比如精确计算、处理表格、批量改文件，换成“模型写代码、程序执行”，准确率就高了。

LangChain 在讲 agent harness 的文章里把 Bash 和代码执行称为通用工具：与其预先设计好 agent 需要的每一个动作，不如给它一个能自己造工具的工具。Claude Code、Codex 这类编程 agent 的工具集都以 shell 为核心，再加上读写文件、搜索之类的少数专用工具。专用工具的意义在于更省 token、更好控制权限，以及给 agent 更明确的使用方式。

代价也很明显。一个能执行任意命令的 agent，也能执行 `rm -rf`，也能把你的密钥发到任何地方。能力越通用，风险越难控制。这个问题留到第 11 篇。

## 4. computer use

还有一种工具，干脆不需要对方提供任何 API：直接操作图形界面。

computer use 的工具很简单：一个截图动作，加上一组鼠标和键盘动作（移动、点击、拖拽、输入文字、按快捷键）。模型看到截图，判断该点哪里，输出一个带像素坐标的点击动作；程序执行后再截一张图发回去。这样循环下去，就能在一个没有 API 的老系统里填表、在网页上订票。

Anthropic 在 2024 年 10 月随 Claude 3.5 Sonnet 推出了 computer use 的公测，OpenAI 随后推出了 Operator。衡量这类能力的常用基准是 OSWorld：在真实的操作系统里完成几百个任务，比如“把这个表格里的数据做成柱状图”。OSWorld 论文（2024）里，人类的完成率是 72% 左右，当时最好的模型只有 12% 左右。之后模型进步很快，但这类任务到今天仍然比调 API 慢得多、贵得多：每一步都要传一张截图，一个任务动辄几十步。

所以实际做法通常是能用 API 就用 API，能读网页的 DOM 或者无障碍树（accessibility tree）就不看截图，实在没有别的办法，才用截图加点击。浏览器自动化是这几种方式的混合地带，第 04 篇会讲到让 agent 用浏览器检查自己做出来的网页。

## 5. MCP

### 5.1 为什么需要一个协议

工具多了，就有一个工程问题。假设有 3 个 agent 应用（Claude Code、Cursor、你自己写的 agent），想接 4 个服务（GitHub、Slack、Postgres、浏览器）。如果每个应用都为每个服务单独写一套集成，就是 12 套，而且每家写法都不一样。

![MCP 把 M×N 的对接变成 M+N](assets/tools/02-mcp.png)

MCP（Model Context Protocol）是 Anthropic 在 2024 年 11 月开源的一个协议，用来解决这个问题。服务方按协议写一个 MCP server，把自己的能力暴露出来；应用方按协议实现一个 MCP client，就能接入任何 MCP server。这样 3 个应用加 4 个服务，只需要 7 份实现。这和 USB、LSP（语言服务器协议，让一个编辑器支持所有语言）是同一个思路。

### 5.2 协议里有什么

一个 MCP server 可以提供三类东西：

- **tools**：可以调用的函数，就是本篇前面讲的工具。
- **resources**：可以读取的数据，比如文件、数据库里的记录。
- **prompts**：预先写好的提示模板，供用户选用。

传输方式有两种：本地进程之间用标准输入输出（stdio），远程服务用 HTTP。

从模型这一侧看，MCP 没有引入任何新东西。MCP client 连上 server 之后，把 server 提供的工具列表转换成普通的工具定义，放进请求的 `tools` 字段。模型输出 `tool_use`，client 把它转发给对应的 server 执行，再把结果作为 `tool_result` 拼回来。模型根本不知道某个工具是不是来自 MCP。MCP 标准化的是工具的提供方式，不是工具调用本身。

### 5.3 现状

MCP 推出一年里被广泛采用，ChatGPT、Gemini、VS Code、Cursor 等都支持了。2025 年 12 月，Linux 基金会成立了 Agentic AI Foundation（AAIF），首批项目是三个：Anthropic 捐出的 MCP，Block 的 agent 框架 goose，以及 OpenAI 的 AGENTS.md（一种给编程 agent 写项目说明的文件约定，第 07 篇会讲）。按 Linux 基金会的公告，当时已经有超过一万个 MCP server。

### 5.4 MCP 的代价

接 MCP server 很方便，方便到很容易接多。每个 server 都会带来一批工具，每个工具的定义都要占上下文。接上五六个 server，几十个工具的定义可能就占了上万个 token，而一次任务里真正用到的只有其中几个。工具多了，模型选错工具的概率也会上升。

另一个问题是安全。MCP server 是第三方写的代码，它返回的内容会直接进入模型的上下文。一个恶意的或者被攻破的 server，可以在工具描述或返回结果里藏指令。第 06 篇讲 Skills 时会讨论怎么按需加载能力，第 11 篇讲这类注入攻击。

## 6. 只调一次工具还不够

到这里，模型能查天气、能读文件、能执行命令了。但回头看第 1 节的伪代码，它只处理了一次工具调用：模型调一次工具，拿到结果，然后回答。

真实的任务很少一步就能完成。修一个 bug，要先搜索相关的文件，读代码，定位问题，修改，然后跑测试；测试没过，还要再读、再改。每一步要做什么，取决于上一步看到了什么。没法事先写好调用顺序，只能让模型自己一步一步决定。

## 小结

- 工具调用的协议是：调用方传入工具定义，模型输出 `tool_use` 表示想调用什么，调用方执行后用 `tool_result` 把结果发回去。模型从不直接执行任何东西。
- 工具定义、调用和结果在序列里都是文本，调用工具的能力是训练出来的。工具定义要占上下文，参数可以用严格模式约束。
- 设计工具时，按 agent 的工作方式来，而不是把 API 原样包一层：合并常用的组合，加命名空间，返回有意义的内容，提供分页和截断，错误信息要说清楚怎么改，描述写得像给新同事看。
- Bash 和代码执行是通用工具，能力强，风险也大。computer use 不需要对方有 API，但慢且贵。
- MCP 把工具的提供方式标准化，把 M×N 的集成变成 M+N。它对模型透明，代价是工具定义容易堆满上下文，也带来第三方代码的安全问题。
