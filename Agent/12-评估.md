# 评估

创建日期：2026-10-17

做 agent 的人每天都在改东西：改一句 system prompt，换一个工具的描述，调整压缩的策略，换一个更新的模型。每次改完都会面对同一个问题：变好了还是变差了？

最常见的做法是凭感觉：拿几个任务试一试，看着还行就上线。问题是 agent 的行为是随机的，同一个任务跑两次结果可能不同；改动的影响也常常在意想不到的地方，修好了 A 场景，B 场景悄悄坏了。没有评估，你只能等用户来告诉你。

[上一篇](11-安全与权限.md)讲完了 harness 的最后一个部件。这一篇讲怎么衡量整个 agent 的好坏。主要参考 Anthropic 在 2026 年 1 月发的《Demystifying evals for AI agents》。

## 1. 术语

![一次 agent 评估由哪些部分组成](assets/eval/01-anatomy.png)

- **任务（task）**：一个测试用例，有明确的输入和成功标准。比如“修复这个 issue，让这组测试通过”。
- **试验（trial）**：对一个任务的一次尝试。因为 agent 的输出是随机的，同一个任务通常要跑多次。
- **运行记录（transcript）**：一次试验的完整记录，包括模型的每一次输出、每一次工具调用、每一个工具结果。
- **结果（outcome）**：试验结束时环境的最终状态。比如代码仓库里的文件、数据库里的记录。
- **评分器（grader）**：给试验打分的程序、模型或人。

还有一个容易被忽略的区分：评估 harness（负责批量运行评估的那套系统）和 agent harness（让模型成为 agent 的那套系统）。文章特别强调，评估“一个 agent”，评的是模型和 agent harness 的组合。同一个模型换一个 harness，结果可能完全不同；同一个 harness 换一个模型，也是如此。

## 2. 三类评分器

**代码评分器。** 跑测试、比对输出、检查文件是否存在、用正则匹配关键内容。快、便宜、客观、可复现。缺点是死板：agent 用了一种完全正确但和预期不同的方法，代码评分器可能判它错。对于写文章、做总结这类主观的任务，也很难写出代码来判断好坏。

**模型评分器。** 让另一个模型按照评分标准打分。灵活，能处理开放式的输出和细微的差别。缺点是本身就有随机性，成本更高，而且需要先和人的判断对一对，确认它打的分靠得住。文章的一个建议是给模型评分器一个“无法判断”的选项，避免它在拿不准时硬编一个分数。

**人工评分。** 质量最高，用来给模型评分器做校准。缺点是贵、慢，没法大规模用。

实际中通常组合使用：能用代码判断的尽量用代码，判断不了的用模型，定期抽一部分让人来检查模型评分器有没有跑偏。

## 3. pass@k 与 pass^k

agent 是随机的，一个任务跑一次成功，不代表每次都成功。描述这种随机性有两个指标。

**pass@k**：跑 k 次，至少成功一次的概率。[推理模型与强化学习](../深度学习/大模型训练/04-推理模型与强化学习.md)第 4.2 节用过这个指标。

**pass^k**：跑 k 次，每次都成功的概率。这个指标由 τ-bench（Yao et al., 2024）提出，专门用来衡量 agent 的稳定性。

假设单次成功率 $p = 0.75$，各次相互独立：

$$
\text{pass@}k = 1 - (1 - p)^k, \qquad \text{pass}^k = p^k
$$

$k = 3$ 时，pass@3 $= 1 - 0.25^3 \approx 98\%$，pass^3 $= 0.75^3 \approx 42\%$。

![pass@k 与 pass^k](assets/eval/02-passk.png)

同一个 agent，看哪个指标，结论完全不同。用哪个取决于使用场景。如果是辅助编程，人会审查每一次输出，失败了重试就行，那么 pass@k 更有意义：只要多试几次能做出来，就是有用的。如果是客服 agent，每个用户只有一次机会，那么 pass^k 更重要：用户关心的是“每次都对”，一个 75% 成功率的 agent 意味着四个用户里有一个会遇到问题。

## 4. 能力评估与回归评估

评估有两种不同的目的。

**能力评估**回答“这个 agent 能做好什么”。任务应该有难度，一开始的通过率应该比较低，这样才能看出改进。如果一套评估一开始就是 95%，它就没法告诉你哪里还能变好。

**回归评估**回答“之前能做的事，现在还能做吗”。通过率应该接近 100%，任何下降都是警报。

两者之间有一个自然的流转：能力评估里的任务，当 agent 稳定通过之后，可以“毕业”进入回归评估，防止以后的改动把它弄坏。

### 4.1 饱和

当 agent 在一套评估上几乎全部通过时，这套评估就饱和了，不再能提供信号。

公开基准也是一样。SWE-bench Verified 是从真实 GitHub issue 里挑出来、经过人工验证的 500 个编程任务，2024 年 8 月发布时最好的成绩只有三四成，一年多以后已经超过 80%。分数接近上限时，剩下的题里有不少本身就有问题（描述不清、测试不对），分数的差别越来越难说明能力的差别。于是又有了更难的基准：Terminal-Bench 考察在命令行环境里完成复杂任务，τ-bench 考察在多轮对话中遵守业务规则并调用工具，OSWorld 考察操作真实的桌面系统（第 02 篇）。

## 5. 怎么开始

Anthropic 的文章给了一套很实用的起步建议。

### 5.1 从真实的失败开始

不需要一开始就建几千个任务的大评估。文章说，从真实失败中挑出的 20 到 50 个简单任务就是一个很好的开始。用户反馈的问题、自己试用时遇到的错误、上线前人工检查发现的毛病，都可以变成任务。

Anthropic 的多 agent 研究系统（第 09 篇）就是这样起步的：一开始只有大约 20 个来自真实使用的查询。早期改动的效果往往很明显，比如成功率从 30% 跳到 80%，几个任务就能看出差别，用不着大样本。

### 5.2 任务不能有歧义

一个好任务的标准是：两个领域专家独立判断，会给出同样的通过或不通过的结论。最好还有一个参考解，证明这个任务是能做出来的。

文章里有一条经验很有用：如果一个任务在很多次试验里都是 0% 通过，通常不是 agent 不行，而是任务本身坏了：描述有歧义，环境配置有问题，或者评分器写错了。

另一个要注意的是正反两面都要测。比如评估一个 agent 什么时候该上网搜索，既要有“应该搜”的任务，也要有“不该搜”的任务，否则优化的结果可能是 agent 什么都去搜一下。

### 5.3 每次试验要隔离

每次试验都应该从一个干净的环境开始。共享状态会让结果互相影响。文章里记录了一个例子：Claude 在评估中翻看了 git 历史，发现了之前试验留下的记录，从而获得了不公平的优势。

### 5.4 评结果，不评路径

检查 agent 产出了什么，而不是它走了哪条路。规定“必须先调用 A 工具、再调用 B 工具”的评分方式太死板，agent 找到一条更好的路反而会被判错。对于由多个部分组成的任务，可以给部分分。

这里有两个例子很能说明问题。

一个是 τ²-bench 里的一道订机票的题。Claude Opus 4.5 找到了航空公司政策里的一个漏洞，给用户提供了一个比标准答案更好的方案。按照题目的评分标准，它“失败”了。

另一个是 CORE-Bench（复现科研论文结果的基准）。Opus 4.5 最初只拿到 42%。研究人员检查后发现，问题出在评估本身：评分过于死板，有些任务描述有歧义，有些任务根本无法复现。修正了这些问题、换用一个限制更少的 harness 之后，分数变成了 95%。

两个例子说的是一件事：分数低的时候，先怀疑评估，再怀疑 agent。

### 5.5 防止钻空子

第 04 篇和第 10 篇都讲过 reward hacking。评估也会被钻空子：agent 可能修改测试，可能找到评分程序的漏洞。评估的设计要保证，通过的唯一途径是真正解决问题。

## 6. 读运行记录

文章里反复强调的一点是：一定要读运行记录。

分数只告诉你通过还是失败，运行记录才告诉你为什么。不读记录，你分不清失败是 agent 的问题还是评分器的问题；你也不会发现 agent 虽然通过了，但是用了一种你不希望它用的方式。

读的时候可以带着几个问题：agent 在哪一步开始偏离的？它当时看到了什么信息？如果我是它，看到这些信息会怎么做？工具返回的东西是不是有误导？

### 6.1 失败归因

找到失败的原因之后，下一个问题是：该改哪里？

同一个表面现象，原因可能在不同的地方。比如 agent 忽略了一个错误、继续往下做了：可能是工具把报错吞掉了，返回了一个看起来正常的结果，那是 harness 的问题；也可能是工具如实返回了报错，模型自己没注意到，那更多是模型的问题。前者改工具，后者改 prompt 或者等更好的模型。

Scale AI 的研究人员在 2026 年 7 月的一篇论文（*Model or Harness?*）里，把这个问题系统化了。他们把 agent 系统拆成模型、harness、用户、工具、记忆、环境几个组件，把每一种失败定位到某两个组件之间的交互上，并标出应该由哪一侧来修：模型这一侧的问题，交给后训练；harness 这一侧的，修脚手架和工具集成；环境或评分器这一侧的，重新设计评估。他们一共整理了 41 种失败模式。

这种归因的价值在于把力气花在对的地方。很多看起来是“模型不够聪明”的失败，其实改一个工具描述就能解决；也有一些失败，harness 怎么改都没用，只能等模型进步。

## 7. 评估之外

评估不是唯一的反馈渠道。文章把它放在一个更大的体系里：上线后的监控、A/B 测试、用户反馈、定期人工审查运行记录、系统性的用户研究。没有哪一层能抓住所有问题。

但评估是这些里面唯一能在上线之前、可重复地运行的。有了一套靠得住的评估，改 prompt、换模型、调 harness 就不再是凭感觉，而是可以量化比较的工程决策。

到这里，这个系列从一次调用讲到了评估，harness 的部件都讲完了。最后一篇，拿一个真实的 harness 对照前面的内容，看这些部件在实际产品里是怎么组合在一起的。

## 小结

- 一次评估由任务、试验、运行记录、结果和评分器组成。评估 agent 评的是模型和 harness 的组合。
- 评分器有代码、模型、人三类，各有利弊，通常组合使用。
- pass@k 衡量“多试几次能不能做出来”，pass^k 衡量“每次都能做对”。单次 75% 的成功率，连续三次都成功只有 42%。
- 能力评估从低通过率开始，看改进；回归评估保持接近 100%，防倒退。评估会饱和，需要不断更新。
- 从 20 到 50 个真实失败开始。任务要无歧义，试验要隔离，评结果不评路径。0% 通过时先怀疑任务本身。
- 一定要读运行记录。找到失败原因后，区分是模型的问题还是 harness 的问题，再决定改哪里。
