# 记忆

创建日期：2026-10-17

[上一篇](06-Skills.md)的 skill 装的是人预先写好的知识：做 PPT 的规范，填表的流程。还有一类信息是在使用中积累出来的：你喜欢简洁的回答，这个项目约定接口统一返回什么格式，上周决定不再用某个库，部署脚本有个坑要先手动清缓存。

这些信息在一次会话里可以靠上下文记住。可会话一结束，上下文就没了，第二天打开，你又得把项目背景从头讲一遍。

这一篇讲 agent 怎么跨会话地记住事情。

## 1. 记忆存在哪里

信息可以存在三个地方。

![信息可以存在三个地方](assets/memory/01-tiers.png)

**权重。** 模型在预训练时学到的知识都在权重里，容量很大，但部署之后就固定了。它知道 Python 怎么写，不知道你的项目。想改它就得微调，代价大，也不适合存“这个用户喜欢什么”这种细碎的、经常变的信息。

**上下文。** 这是模型真正“看得见”的工作区。前面几篇讲的都是它：每次调用时拼进去，调用结束就消失，容量有限，越长越贵也越不准。

**外部存储。** 文件、数据库、向量库。容量几乎不限，跨会话保存，但模型看不到它，必须通过工具读进上下文才能用。

agent 的“记忆”主要指第三种：存在上下文之外，跨会话保存，并且由 agent 自己决定读什么、写什么。

2023 年的 MemGPT 论文（Packer et al.）用操作系统打了个比方：上下文窗口像内存，外部存储像磁盘。内存小而快，磁盘大而慢，操作系统负责在两者之间换入换出数据。MemGPT 让模型自己扮演这个操作系统，用函数调用来决定把什么从上下文移到外部，把什么从外部调回上下文。这个项目后来发展成了 Letta。

## 2. 文件式记忆

最简单、也是目前编程 agent 用得最多的做法，是把记忆写在普通的文本文件里。

### 2.1 项目说明文件

Claude Code 的 `CLAUDE.md`，OpenAI Codex 等工具的 `AGENTS.md`，都是这一类。它是放在项目根目录下的一个 Markdown 文件，agent 每次启动时自动读进上下文。里面写项目的结构、构建和测试命令、代码规范、一些需要注意的约定。`AGENTS.md` 在 2025 年 12 月和 MCP 一起成为 Agentic AI Foundation 的首批项目（见第 02 篇）。

这类文件通常可以有好几层：用户级别的（对所有项目生效的个人偏好），项目级别的（提交进仓库、团队共享），还有子目录级别的（只在处理那个目录时加载）。

这类文件每次都会被完整读进上下文，所以它和上一篇讲的 skill 元数据一样，是固定成本。写得越长，每一轮付的钱越多，重要的规则也越容易被淹没。

### 2.2 目录，不是百科全书

OpenAI 在《Harness engineering》里讲过他们踩的坑（据转述）。一开始他们想把所有规则都写进一个大的 `AGENTS.md`，结果失败了：文件太长，挤占了任务本身的上下文，模型也抓不住重点。最后的版本只有大约 100 行，作用是导航，指向 `docs/` 目录下结构化的知识库：设计文档、执行计划、架构决策、质量评分。agent 需要哪部分，再顺着链接去读。

这其实就是第 05 篇的“只放线索，用到再取”和第 06 篇的“三级加载”用在了记忆上：常驻的部分只是一份目录，具体内容按需读取。

那篇文章里还有一句话，据转述大意是“Codex 看不到的东西就不存在”。团队在 Slack 里讨论定下的事、在 Google 文档里写的设计，如果没有落到仓库里，agent 就永远不会知道。对 agent 来说，记忆的边界就是它能访问的文件的边界。

### 2.3 agent 自己写的记忆

项目说明文件多半是人写的。更进一步，可以让 agent 自己记笔记。

Anthropic 在 2025 年 9 月推出了一个 memory tool：给模型一个专门的 `/memories` 目录，以及在里面查看、创建、修改、删除文件的工具。模型在开始任务前先看看这个目录里有什么，在工作中把值得记住的东西写进去。存储放在调用方自己的系统里，开发者完全掌控。

一个常见的组织方式是：

```text
memories/
├── MEMORY.md                 # 索引，每条一行：标题 + 链接 + 一句话说明
├── user-preferences.md       # 每个文件只记一件事
├── project-api-conventions.md
└── feedback-no-mock-db.md
```

索引文件每次会话开始时读进上下文，具体的记忆文件在相关时才读。每个文件只记一件事，方便单独更新和删除。

文件式记忆的好处是透明：人可以直接打开文件看 agent 记了什么，记错了就改，不想要了就删。

## 3. 检索式记忆

记忆多到成千上万条，或者内容是大量非结构化的对话记录时，靠文件名和索引就不够了。这时常用的是检索：把每条记忆转成向量存起来，需要时把当前的问题也转成向量，找出最相近的几条放进上下文。这和 RAG 的做法完全一样，区别只在于检索的对象是 agent 自己的经历，而不是外部的文档库。

光看语义相似度还不够。2023 年斯坦福的 Generative Agents 论文（Park et al.）让 25 个由大模型驱动的角色在一个虚拟小镇里生活，每个角色都有一个记录所见所闻的“记忆流”。检索时，每条记忆按三个分数加权：时间上有多近，有多重要（由模型打分，比如“吃早餐”不重要，“和人吵架”重要），和当前情境有多相关。这个设计到今天仍然是很多记忆系统的参考。

文件和检索怎么选？大致的原则是：记忆量少、结构清楚、需要人能看懂和修改的，用文件；记忆量大、内容零散、主要靠语义找的，用检索。第 13 篇会讲到，Claude Code 在代码检索上选择了 `grep` 而不是向量索引，记忆上也选择了纯文本文件，背后是同一种对简单、透明、不会过时的偏好。

## 4. 写入

读记忆相对简单，难的是写。写什么、什么时候写、写错了怎么办，每个问题都没有标准答案。

![记忆的读、写与整理](assets/memory/02-lifecycle.png)

### 4.1 写什么

值得记的，是那些下次还会用到、而且没法从别处轻易得到的信息：

- 用户的偏好和习惯：喜欢什么风格，讨厌什么做法。
- 用户的纠正：上次做错了什么，用户希望怎么做。最好连原因一起记下，下次遇到相似但不完全相同的情况，才能判断这条规则适不适用。
- 做过的决定：为什么选了方案 A 而不是 B。
- 踩过的坑：某个命令在这台机器上要加什么参数。

不值得记的，是那些随时能查到的东西：代码结构（读代码就知道），git 历史（`git log` 就有），完整的对话记录（太长，没有提炼）。记忆是对经验的提炼，不是日志。

### 4.2 写错了怎么办

记忆写进去以后，下次会被当成事实读回来。这是记忆系统最大的风险。

写错是一种情况。模型误解了用户的一句话，把一个临时的要求记成了永久的偏好，以后每次都照着做。

过时是另一种情况。三个月前记下“测试用 `npm test` 运行”，后来项目换了构建工具，这条记忆就是错的了。记忆里提到的文件、函数、配置项，使用前最好核实一下它们是否还存在。

矛盾也很常见。上个月记了“用户喜欢详细的解释”，这个月又记了“用户嫌回答太长”。两条都在，模型不知道听哪条。所以写入前要先查有没有相关的旧记忆，有就更新，而不是再新建一条。

### 4.3 记忆注入

最危险的情况是记忆被人故意写错。

第 11 篇会讲 prompt injection：模型读到的网页、邮件、文档里可能藏着恶意指令。没有记忆时，注入的影响只在一次会话里；有了记忆，攻击者可以让模型把恶意指令写进记忆，从此每次会话都会读到它。2024 年，安全研究员 Johann Rehberger 演示过针对 ChatGPT 记忆功能的这类攻击：通过一个恶意网页，让 ChatGPT 记住一条指令，把之后所有对话内容发送到攻击者的服务器。

所以写入记忆应该是一个比普通操作更谨慎的动作。读过不可信内容之后的写入尤其要小心，必要时让用户确认。

## 5. 整理

记忆会越积越多，需要定期整理：合并重复的，删掉过时的，解决矛盾的，把零散的细节提炼成更概括的认识。

Generative Agents 里有一个叫“反思”的机制：重要的记忆积累到一定量时，让模型回顾最近的记忆，提炼出更高层次的结论（比如从一连串观察里总结出“某某对音乐很有热情”），作为新的记忆存回去。

整理不一定要在会话中做。Letta 在 2025 年提出了“睡眠时计算”（sleep-time compute）：主 agent 和用户交互的同时，另一个 agent 在后台异步地整理记忆，或者在用户不在的时候提前做好准备。整理很花 token，但不需要实时完成，放到后台既不拖慢交互，也可以用更便宜的方式来跑。

也有人把记忆放进 git 仓库，每次修改都是一次提交。记错了可以回滚，也能看到某条记忆是什么时候、因为什么写进去的。

## 6. 记忆与上下文工程

讲到这里，记忆和第 05 篇的上下文工程有很多重叠：压缩是把对话变短后留在上下文里，结构化笔记是把信息写到上下文外面再读回来，记忆也是。

大致可以这样区分：上下文工程管的是一个上下文窗口之内放什么；记忆管的是信息怎么跨越上下文窗口。第 05 篇那个玩宝可梦的例子正好在两者的交界上：笔记是为了在同一个长任务里，上下文被清空之后还能接着做。

同一个任务跨越多个上下文窗口，这本身就是一类问题，下一篇专门讲。

## 小结

- 信息可以存在权重、上下文和外部存储里。agent 的记忆指的是外部存储里、由 agent 自己读写、跨会话保存的那部分。
- 文件式记忆最简单透明。`CLAUDE.md`、`AGENTS.md` 这类文件每次都会加载，应该写成一份目录，具体内容按需读取。
- 记忆量大、内容零散时用向量检索，可以结合时间、重要性和相关性加权。
- 写入是最难的部分：只记下次用得上、别处查不到的东西；写入前先查旧记忆，有就更新；使用前核实是否过时。
- 记忆可能被注入恶意指令，影响会持续到之后的每一次会话。
- 记忆需要整理，可以放到后台异步做。
