# 长时任务：跨越多个上下文窗口

创建日期：2026-10-17

前面几篇的 agent 都在一个上下文窗口里干活。第 05 篇讲了怎么让这个窗口用得更久：卸载、清除、压缩。但有些任务注定一个窗口装不下。从零搭一个网站，迁移一个大型代码库，把一个几百页的需求文档实现出来，这些任务要做几个小时甚至几天，中间不知道要读多少文件、跑多少次测试。

[上一篇](07-记忆.md)讲了跨会话的记忆：记住用户和项目的情况。这一篇要解决的问题更具体：同一个任务，怎么让一个接一个的上下文窗口接力完成，而且每一棒都知道前面做到了哪里。

## 1. 两种失败

Anthropic 在 2025 年 11 月的工程博客《Effective harnesses for long-running agents》里，记录了让 Claude 从零开始搭建一个 claude.ai 克隆网站的实验（第 04 篇提过这个实验的验证部分）。他们先试了最直接的做法：给一个高层的需求，让 agent 跑，上下文满了就压缩，接着跑。结果观察到两种典型的失败。

**一口气做太多。** agent 试图一次把整个应用写完，写到一半上下文耗尽了。下一个会话接手时，面对的是一个写了一半、没有任何说明的功能，只能花大量时间猜测前面发生了什么，再把应用恢复到能跑的状态。

**过早宣布完成。** 项目进行到后期，一个新会话的 agent 看了一眼，发现已经有很多功能做好了，就宣布整个任务完成。实际上还有很多功能没做。

两种失败的根源是一样的：每个新的上下文窗口都是从零开始的，它对任务全貌的了解，只来自它在开场时能看到的东西。压缩留下的摘要不一定够用，而且摘要本身可能漏掉了关键信息。

## 2. 把状态放到上下文之外

解决办法是不依赖上下文来传递状态，而是把状态写在磁盘上。

上下文窗口像是一个工程师的短期记忆，会话结束就清空了；磁盘上的文件和 git 历史像是项目的文档和代码库，谁来接手都能看。好的交接，靠的是后者。

具体要写什么，取决于下一个会话需要知道什么：任务的全貌是什么（还有哪些没做），现在做到了哪里（刚做完什么，有没有遗留问题），怎么让环境跑起来，以及代码本身的历史。

## 3. 初始化 agent 与工作 agent

Anthropic 那个实验的最终方案，把会话分成了两种角色。

![多个会话之间的接力](assets/long/01-relay.png)

### 3.1 初始化 agent

第一个会话只做准备工作，不写功能代码：

- **写功能清单。** 把高层需求展开成一份详细的功能列表。对于 claude.ai 克隆，这份清单有两百多项，比如“用户可以新建一个对话，输入问题，收到 AI 的回答”。每一项都有描述、测试步骤和一个 `passes` 字段，初始全部是 `false`。
- **写启动脚本 `init.sh`。** 一条命令把开发服务器跑起来。
- **建进度文件 `claude-progress.txt`。** 记录每个会话做了什么。
- **做第一次 git 提交。**

功能清单为什么用 JSON 而不是 Markdown？文章的解释是，模型更不容易随手改写或覆盖 JSON 文件。清单是整个项目的“合同”，后续的 agent 只允许修改 `passes` 字段，不允许删改测试项。第 04 篇引用过那句措辞很重的指令：删除或修改测试是不可接受的。

有了这份清单，“过早宣布完成”就很难发生了：清单上还有 `false`，任务就没完。

### 3.2 工作 agent

之后的每个会话都是工作 agent。它和初始化 agent 用的是同一个模型、同一套工具，区别只在于初始的 prompt。

工作 agent 每次只做一项功能。这是解决“一口气做太多”的关键：一项功能的工作量，一个上下文窗口装得下。做完以后，用浏览器端到端测试一遍，通过了就把 `passes` 改成 `true`，写一条描述清楚的 git 提交，更新进度文件。这样，即使这个会话在中途意外中断，项目也停在一个干净的、可以回滚的状态。

### 3.3 开场流程

每个工作 agent 开场时都走一遍固定的流程：

```text
1. pwd                                   # 确认自己在哪个目录
2. 读 claude-progress.txt 和 git log      # 知道之前发生了什么
3. 读功能清单，挑优先级最高的未完成项
4. 运行 init.sh 启动开发服务器
5. 先做一次基本的端到端测试               # 确认现有功能没坏
6. 开始做新功能
```

第 5 步容易被忽略，但很重要。上一个会话可能留下了一个没发现的 bug。如果不先检查就开始做新功能，新旧问题会搅在一起，很难排查。先确认基线是好的，再往上加东西。

这个流程和一个工程师早上到岗后做的事差不多：看看昨天的提交，看看任务看板，把环境跑起来，确认没问题，然后开始今天的工作。

## 4. Ralph 循环

还有一种更简单粗暴的做法。Geoffrey Huntley 在 2025 年 7 月介绍了一种他称为 Ralph 的方法（名字来自《辛普森一家》里那个憨憨的小孩 Ralph Wiggum），核心只有一行：

```text
while :; do cat PROMPT.md | claude-code ; done
```

一个死循环，每次都把同一份 prompt 喂给编程 agent。agent 干完一轮就退出，循环马上开下一轮，每一轮都是全新的上下文。

### 4.1 文件

状态全部在文件里：

- `PROMPT.md`：每一轮都相同的指令。
- `specs/`：需求规格，一个文件一个主题，在开始前和 agent 对话写出来。
- `fix_plan.md`：按优先级排好的待办列表。agent 每轮从里面挑最重要的一项来做。
- `AGENT.md`：怎么构建、怎么运行这个项目。agent 学到新东西时自己更新它。

每轮只做一件事，这样上下文用量很低，也不容易做歪。主上下文只负责调度，搜索代码、写文件这些耗上下文的工作交给子 agent（第 09 篇）。

### 4.2 反压

Ralph 能工作的前提是第 04 篇讲的反压：测试、类型检查、静态分析会拒绝有问题的代码。Huntley 还特别要求测试代码里写注释，说明这个测试为什么存在，因为后面的循环不会记得当初的理由。

### 4.3 失败模式

Huntley 也坦白地列了 Ralph 常见的问题：

- **占位实现。** 模型倾向于写一个最小的桩函数就交差。prompt 里要明确要求完整实现。
- **重复实现。** agent 用 `ripgrep` 搜索时，搜索结果不总是可靠，它可能误以为某个功能还没实现，于是又写了一遍。对策是在 prompt 里要求“先搜索，不要假设没有”。
- **代码库被改坏。** 有时候只能用 git 回退，重新开始循环。

他对这个方法的评价是：“在一个不确定的世界里，它确定地很糟糕”（deterministically bad in an undeterministic world）。意思是它的失败方式是可预期的，可以通过调整 prompt 和反压一点点改进。他认为 Ralph 适合从零开始的新项目，能做到九成左右；用在已有的代码库上，他自己说绝对不会这么干。

LangChain 的 harness 文章里把 Ralph 描述成一种 harness 模式：用一个 hook 拦截 agent 想要退出的动作，把原始 prompt 重新注入一个干净的上下文窗口，强迫它继续朝目标推进，状态通过文件系统在每一轮之间传递。

## 5. 规划

长任务的另一个关键是在动手之前先想清楚。

**先写规格。** Ralph 的 `specs/` 和 Anthropic 的功能清单都是这个作用：把模糊的需求变成具体的、可以逐项验证的条目。这一步通常需要人参与，因为只有人知道自己真正想要什么。

**先探索，再计划，再执行。** 很多编程 agent 提供了“计划模式”：agent 只能读代码、不能修改，先把相关的代码摸清楚，写出一份实施计划，人看过同意以后再开始改。这把“理解问题”和“解决问题”分开了，人在成本最低的时候介入。

**任务清单。** 一个会话之内，agent 可以维护一个 todo 列表，开始时列出步骤，每完成一步勾掉一项。第 05 篇讲过，这份列表反复出现在上下文末尾，能帮模型保持方向。长任务里，这份列表就是写在磁盘上的 `fix_plan.md` 或功能清单。

## 6. agent 能独立工作多久

这一篇讲的都是 harness 怎么帮 agent 撑过更长的任务。模型本身能独立处理多长的任务，也在快速增长。

METR 在 2025 年 3 月提出了一个衡量指标：任务时长（time horizon）。做法是收集一批软件和研究任务，先请人类专家来做，记录每个任务要花多久；再让 agent 来做，看它在多长的任务上还能有 50% 的成功率。这个“50% 成功率对应的人类耗时”，就是这个 agent 的任务时长。

![METR 的任务时长指标](assets/long/02-horizon.png)

论文摘要里给出的结论是：当时的前沿模型，比如 Claude 3.7 Sonnet，任务时长大约是 50 分钟；2019 年以来，这个指标大约每 7 个月翻一倍，2024 年可能还在加速。如果趋势持续，五年内 agent 就能完成很多今天人类要花一个月的软件任务。

这个指标要谨慎地看。50% 的成功率对实际使用来说很低，要求更高的成功率时，对应的任务时长要短得多。这些任务也大多是边界清楚、可以自动评分的软件任务，真实工作要混乱得多。METR 自己也说明了，外推的前提是这些结果能推广到真实的软件工作中，而这本身还是个开放问题。

但趋势本身说明了一件事：harness 的设计要跟着模型的能力调整。今天需要拆成二十个会话的任务，一年后可能五个就够了；今天必须写进 prompt 的约束，以后可能不再需要。第 10 篇会讨论模型和 harness 之间的这种此消彼长。

## 7. 一个窗口里装太多

回到单个会话。即使只做一项功能，agent 也常常要在一个上下文里装下很多东西：搜索代码库找相关文件，读文档，查资料，写代码，跑测试。搜索和阅读产生大量的中间结果，但最后真正有用的往往只是几行结论：“相关的代码在这三个文件里”“这个 API 的用法是这样的”。

## 小结

- 长任务的两种典型失败：一次做太多，做到一半上下文耗尽；后来的会话看到部分进展，过早宣布完成。
- 根源是每个上下文窗口都从零开始。解决办法是把状态写在磁盘上：功能清单、进度文件、启动脚本、git 历史。
- 初始化 agent 只做准备：展开功能清单（JSON，初始全为 false）、写启动脚本、建进度文件。工作 agent 每次只做一项功能，测试通过后提交并更新进度。
- 每个会话开场走固定流程：确认目录、读进度和 git log、挑任务、启动环境、先验证基线。
- Ralph 用一个死循环反复喂同一份 prompt，每轮全新上下文、只做一件事，靠文件传状态、靠测试施加反压。适合新项目。
- METR 的任务时长指标约每 7 个月翻一倍。harness 的设计要随着模型能力调整。
