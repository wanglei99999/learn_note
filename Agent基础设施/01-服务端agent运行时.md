# 服务端 agent 运行时

在本机命令行里运行的 agent，状态都在一个进程里：对话在内存里，文件在当前目录，输出直接打到终端，进程退出，一切随之结束，用户也就在旁边。把同一个 agent 放到服务端，让很多用户通过网页或接口使用它，模型调用的方式没有变，变的是状态的处境：状态被拆到了不同的地方，每一处都可能在任何时刻失效。

服务端 agent 运行时管理三份状态：会话状态（对话记录和运行进度），执行环境的状态（沙箱里的文件和进程），以及客户端看到的状态（事件流）。三者生命周期不同，失效的方式也不同。运行时的工作，是在进程崩溃、连接中断、沙箱回收之后，让这三份状态重新一致，并且在做不到完全一致时，让模型和用户都知道哪里不一致。这篇笔记给出这三份状态的划分，以及系列中其他几篇各自处理的是哪一处不一致；具体机制在各篇里展开。

## 1. 三份状态

### 1.1 会话状态

会话状态是对话记录加上运行进度：哪些条目已经写入，哪个模型回合正在进行，哪些工具调用发出了但还没有结果，哪些输入在排队。它必须比服务端进程活得久：发布新版本、机器维护都会重启进程，会话不能因此丢失或重复执行。

这一层由持久化引擎负责。pi-durable 的做法是所有状态先提交再展示，工具调用先提交意图再执行，崩溃后对执行到一半的工具如实报告中断。它保证的是至多一次，不是恰好一次（见[持久化执行](04-持久化执行.md)）。

### 1.2 执行环境的状态

执行环境的状态是沙箱里的文件系统和进程。harness 不进沙箱时，它和会话状态分在两个地方：会话在服务端的存储里，文件和进程在沙箱里（见[harness 的位置](02-harness的位置.md)）。服务端通过执行通道操作沙箱，每个文件操作和命令都是一次远程调用（见[执行通道](03-执行通道.md)）。

两份状态的恢复能力不对等，由此产生三种不一致：

| 事件 | 会话状态 | 执行环境 | 不一致 | 处理 |
|---|---|---|---|---|
| 会话分叉到历史条目 | 回到该条目 | 仍是现在的文件 | 文件比对话超前 | 检查点：在对话位置留文件系统快照（[沙箱检查点](06-沙箱检查点.md)） |
| 服务端崩溃重启 | 从断点继续，报告中断 | 旧命令可能还在运行 | 两个所有者同时写工作区 | epoch 隔离：新连接开始前清理旧进程（[崩溃后的旧进程](05-崩溃后的旧进程.md)） |
| 沙箱被回收或丢失 | 完整 | 不存在了 | 对话里做过的事在环境里没有了 | 从检查点重建，写一条模型可见的说明 |

第三行里的"说明"是贯穿各处的原则：环境与对话不一致而又无法修复时，往会话里写一条模型看得见的条目，告诉它哪些操作在当前环境里没有发生。模型据此决定是否重做，而不是在一个它以为熟悉、其实已经变了的环境里继续工作。

### 1.3 客户端看到的状态

用户在网页上看到的是第三份状态：会话的当前视图，加上流式到来的增量。它要满足两条：客户端看到过的内容，服务端存储里一定有；断线重连后，客户端能拿到完整的当前状态。

第一条由"先提交再展示"保证。第二条在 pi-durable 里的实现是：重连时先发一份当前的完整视图，之后再发增量；客户端落后太多时，也用一份新的完整视图代替积压的增量。它不回放错过的增量，对客户端来说足够正确，代价是每次重连都要传一次完整视图。Tether 把沙箱状态变化、检查点这类事件也写成会话里的条目，和模型的回答走同一条提交线，客户端看到的事件顺序因此天然和会话一致。

## 2. 运行时的组成

把三份状态各自交给一个组件，运行时的结构就确定了。Tether 第一阶段的组成如下：

```text
客户端（SDK / CLI / 以后的 App）
        │ HTTP + WebSocket
┌───────▼───────────────────────────────────────────┐
│ 领域服务：agent 定义与版本、会话、检查点策略、准入  │
├──────────────┬──────────────────┬──────────────────┤
│ AgentEngine  │ SandboxProvider  │ ExecChannel      │
│ 会话状态      │ 沙箱生命周期      │ 执行通道 + 隔离   │
│ pi-durable   │ Docker           │ pi-env           │
└──────────────┴──────────────────┴──────────────────┘
```

每个组件前面都有一个由 Tether 自己定义的接口，pi 的类型只出现在适配层里。第一阶段用 pi 的现成实现，第二阶段逐个换成自己的实现：自研的执行 daemon、Firecracker 后端、持久化引擎、带序号续传的事件同步。每个接口有一套与实现无关的一致性测试，pi 的实现先通过它，自己的实现也必须通过同一套测试。

沙箱后端的选择决定了"执行环境的状态"能保存到什么程度。普通容器和 gVisor 只能保存文件系统，microVM 还能保存内存里的进程（见[沙箱后端](07-沙箱后端.md)）。Tether 第一阶段用 Docker，所以检查点只有文件，恢复和分叉后正在运行的后台服务都需要重新启动。

## 3. 一致性要靠测试证明

上面每一条"保持一致"的说法，都对应一种故障：进程在某个时刻被杀，连接在某个时刻卡住，沙箱在某个时刻消失。这些故障只在特定的时间点才会暴露问题，正常运行时的测试覆盖不到。

Tether 用混沌测试来验证：以子进程方式启动服务端，用脚本化的假模型驱动固定的 agent 行为，在随机时间点杀进程、断网、删沙箱，然后检查不变式：

1. 每个 `requestId` 最多对应一次运行。
2. 不能重放的工具没有被执行两次，用沙箱里的执行记录核对。
3. 重连之后，沙箱里不存在上一个 epoch 的存活进程。
4. 环境与对话不一致时，会话里一定有对应的说明。
5. 已提交的事件，客户端重连后都能看到。

随机种子固定，失败可以复现。README 里的每一条可靠性说法，都要对应其中一条不变式和它跑过的轮数。

## 4. 结论

服务端 agent 运行时的难点在状态，不在推理。会话状态、执行环境的状态、客户端看到的状态，分在三个地方，生命周期和失效方式各不相同。运行时的工作是让它们在故障之后重新一致：持久化引擎让会话比进程活得久，检查点和 epoch 隔离让执行环境跟上会话，先提交再展示让客户端不会看到存储里没有的东西。

做不到完全一致的地方，运行时要如实告诉模型和用户。一个运行时可不可信，取决于两件事：它承诺的每一种一致性有没有被注入故障的测试验证过，以及它在无法恢复时，是让不一致悄悄发生，还是把它写进会话里。
