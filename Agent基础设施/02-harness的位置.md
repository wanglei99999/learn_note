# harness 的位置

一个 agent 由模型和 harness 组成。harness 是模型之外的那部分程序：组装上下文、调用模型、解析工具调用、执行工具、保存会话。把 agent 放到服务端运行时，第一个架构决定是 harness 放在哪里：和工具一起放进沙箱，还是留在服务端，只把工具执行送进沙箱。

这个决定划定了三条边界：凭据在哪里，会话状态在哪里，资源在什么时候被占用。多租户的服务端 agent 一般选择 harness 不进沙箱，因为三条边界都更容易守住；代价是每次工具调用都要跨一次进程边界，并且会话状态和沙箱状态分在两处，需要额外的机制让它们保持一致。这篇笔记逐一分析这三条边界和两项代价。文中的轮数、延迟是构造的示意，数字可以手算核对。

## 1. 两种布局

```text
harness 进沙箱                              harness 不进沙箱

服务端                                      服务端
┌───────────────┐                           ┌────────────────────────────┐
│ 调度、转发消息 │                           │ harness：上下文、模型调用、 │
└──────┬────────┘                           │ 工具调度、会话存储、凭据    │
       │                                    └──────────┬─────────────────┘
       ▼                                               │ 每次工具调用
┌──────────────────────────┐                           ▼
│ 沙箱                      │                ┌──────────────────────────┐
│ harness + 工具 + 工作区   │                │ 沙箱                      │
│ 会话状态、模型 API key    │                │ 执行 daemon + 工作区      │
└──────────────────────────┘                └──────────────────────────┘
```

左边的布局里，沙箱是一个完整的 agent 运行环境，服务端只负责启动容器、把用户消息转进去、把输出转出来。现成的命令行 agent（Claude Code、Codex CLI）不用改代码，整个放进容器就能在云上运行。

右边的布局里，沙箱只是一个远程的文件系统和进程空间。ChatGPT 的代码执行属于这一类：对话和模型在服务端，只有代码被送进隔离环境执行。E2B 这类沙箱服务的接口也是按这个布局设计的：创建沙箱、在里面执行命令、读写文件，agent 循环由调用方自己运行。pi-durable 加 pi-env 是同样的结构，工具通过 `ExecutionEnv` 接口在远端执行（见[执行通道](03-执行通道.md)）。

## 2. 凭据的边界

harness 要调用模型，就要持有模型的 API key。

harness 进沙箱时，key 必须进入沙箱，或者在沙箱外面架一个代理，由代理在请求经过时注入 key。前一种做法意味着模型写出的任何命令都可能读到它：`env`、`cat /proc/self/environ`，或者一段打印环境变量的测试脚本。沙箱的隔离保护的是宿主机，不保护沙箱里的东西不被沙箱里的代码读到。后一种做法要求沙箱的所有出站流量都经过代理，代理还要能识别哪些请求是发给模型服务的。CubeSandbox 0.4 版本的凭据库（credential vault）就是这种做法，文档的描述是"agent 照常调用外部 API，密钥从不进入沙箱"。

harness 不进沙箱时，key 一开始就在服务端，沙箱里没有任何东西需要它。只要服务端不把 key 放进执行请求的环境变量，模型写出的命令就读不到。凭据的边界和沙箱的边界重合，不需要额外的机制。

同样的道理也适用于其他凭据。agent 需要推送代码时，Git token 放在哪里，需要单独设计；但在 harness 不进沙箱的布局里，至少模型服务的 key、会话存储的连接串、其他租户的数据，天然不在沙箱的可见范围之内。

## 3. 状态的边界

### 3.1 会话状态的归属

harness 进沙箱时，会话记录、运行状态都在容器里。容器被回收或者宿主机故障，会话就随之丢失，除非 harness 提前把状态同步到外部存储。而同步要在 harness 内部实现：现成的命令行 agent 通常把会话写在本地文件里，没有为容器随时消失这种情况做设计。

harness 不进沙箱时，会话状态在服务端的存储里。沙箱可以随时销毁重建，会话不受影响；服务端进程崩溃，重新打开存储就能从断点继续（见[持久化执行](04-持久化执行.md)）。多个客户端订阅同一个会话、断线重连后拿到完整状态，也都建立在状态集中保存的基础上。

### 3.2 两份状态的一致性

状态集中在服务端也带来了一个新问题：会话状态和沙箱状态分在两处，两处的恢复能力不对等。会话记录可以分叉到任意一个历史条目，沙箱的文件系统只有当前这一份（见[沙箱检查点](06-沙箱检查点.md)）；服务端崩溃后会话能续上，沙箱里旧连接启动的命令却可能还在运行（见[崩溃后的旧进程](05-崩溃后的旧进程.md)）。

harness 进沙箱时这个问题不存在，因为两份状态在同一个地方，同生同灭。harness 不进沙箱，等于主动把状态拆开，换取凭据隔离和会话的持久性，然后用检查点、epoch 隔离这些机制把两边重新对齐。Tether 第一阶段最难的部分都在这里。

## 4. 资源的边界

agent 的大部分时间花在等模型上。设一个编码任务跑 30 轮，每轮模型生成平均 8 秒，工具执行平均 2 秒，总计 300 秒，其中工具执行 60 秒，占 20%（示意）。

harness 进沙箱时，容器在整整 300 秒里都在运行，因为 harness 就在里面。剩下 80% 的时间，容器在等一个 HTTP 响应，占着内存，什么都不算。

harness 不进沙箱时，沙箱只在工具执行时被使用。工作区要一直保留，所以沙箱不能在两次工具调用之间销毁；但它可以在会话闲置一段时间后停止，释放内存，下次工具调用时再启动。Tether 的闲置策略是闲置 1 小时停止容器、7 天删除，停止时写一条模型可见的说明，告诉模型后台进程已经结束。harness 在服务端，服务端进程可以同时运行成百上千个会话的 agent 循环，它们大部分时间都在等模型，CPU 占用很低。

## 5. 代价

### 5.1 每次工具调用跨一次进程边界

harness 不进沙箱，每次读文件、写文件、执行命令都是一次远程调用。一个编码任务的工具调用常常是几百次：读几十个文件、搜索、编辑、跑测试。

以 300 次工具调用为例（示意）：本地 Docker 后端走 `docker exec` 的管道，单次往返在毫秒级，累计不到一秒；远程后端每次往返 100 ms，累计 30 秒，相对于 300 秒的总时长多了 10%；服务端在国内、沙箱在海外时往返可能更长。

执行通道可以缓解一部分：小请求的回复排在大块输出前面，命令输出按调用方的需要裁剪，完整输出留在沙箱里只传末尾（见[执行通道](03-执行通道.md)）。往返次数本身减少不了，除非把多次调用合并成一次，比如 code mode 让模型写一段脚本，在一次调用里完成多次文件操作。

### 5.2 两份状态要对齐

这是 3.2 节说的问题的另一面：它不只是设计上的难点，也是实现和测试的成本。检查点要和对话位置对齐，崩溃后要清理旧进程，沙箱丢失后要从检查点重建并告诉模型。每一条都需要混沌测试去验证：在随机的时间点杀进程、断网、删沙箱，检查不变式是否成立。harness 进沙箱的布局不需要这些测试，因为它根本不承诺这些能力。

## 6. 适合进沙箱的场景

harness 进沙箱在三种情况下是更好的选择：

- **复用现成的 agent。** Claude Code、Codex CLI 本身就是完整的 harness，想在云上跑它们又不改代码，整个放进容器是最省事的办法。
- **工具调用极其密集，且后端在远处。** 每轮都要读写几百个文件的任务，远程往返的累计延迟可能超过模型生成的时间。
- **单人、一次性的任务环境。** 没有多租户，没有长期保存的会话，任务结束容器就丢弃。凭据和状态的边界都不重要，简单是优点。

## 7. 结论

harness 的位置决定了三条边界：凭据、会话状态、资源占用。harness 留在服务端时，三条边界都和沙箱的边界重合，凭据不进沙箱，会话不随沙箱消失，沙箱只在工具执行时需要运行。代价是每次工具调用跨一次进程边界，以及会话和沙箱两份状态需要额外的机制对齐。

选哪一种取决于三个条件：是否多租户、是否需要长期保存和恢复会话，以及工具调用的密度和沙箱后端的距离。多租户、要持久会话的服务端 agent，选择 harness 不进沙箱，并为状态对齐付出工程成本；复用现成 agent、单人一次性使用、工具调用密集而后端很远的场景，harness 进沙箱更合适。
