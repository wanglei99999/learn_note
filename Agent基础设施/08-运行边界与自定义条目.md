# 运行边界与自定义条目

服务端运行时有两件事必须在持久化引擎内部完成。第一件是在每一轮运行开始时动手：[第 6 篇](06-沙箱检查点.md)的 `perRun` 策略要在一轮运行发出第一个模型请求之前打快照，并把快照对齐到触发这一轮的用户输入。第二件是把运行时自己的事件写进对话：沙箱状态变化、检查点、"工作区已重置"这类说明，有的只给客户端看，有的必须让模型知道（[第 1 篇](01-服务端agent运行时.md)的原则）。

两件事都依赖引擎内部状态的粒度。识别一轮运行，要找在整轮里保持不变的那个标识，即触发这一轮的提交，而不是此刻负责推进它的任务；用错了粒度，检查点会按模型回合而不是按轮次打。自定义条目能不能被模型看到，由条目的 `model` 字段决定；什么时候进入模型的上下文，由引擎的边界决定。这篇笔记以 pi-durable 1.3.0 为对象，结论来自 Tether M0 Task 7 的实测，条目、文档、任务的基本概念见[第 4 篇](04-持久化执行.md)。

## 1. 一轮运行在存储里的形状

### 1.1 提交、generation、tool

[第 4 篇](04-持久化执行.md)的 2.2 节给出了一次回答的任务结构：一条输入成为 `pi.user` 条目，每个模型回合是一个 `pi.generation` 任务，它拥有本轮的 `pi.tool` 任务。M0 的实验让 faux 模型在第一轮先调用一个空工具 `noop` 再回答，第二轮直接回答，存储里的编号是这样的：

```text
提交 8：输入 "run 1"   → pi.user 条目
  generation 9     模型：调用 noop
    tool           执行 noop → pi.tool-result
  generation 14    模型："ok1"
提交 8 完成

提交 17：输入 "run 2"  → pi.user 条目
  generation 18    模型："ok2"
```

一轮运行里有几个模型回合，就有几个 generation 任务。贯穿整轮、始终不变的只有触发它的那条提交。提交和任务的编号看起来出自同一个递增序列（8、9、14、17、18 之间的空号被工具任务等占用），这是从数字上观察到的，没有在源码里核对。

### 1.2 钩子挂在 generation 上

扩展可以给内置任务挂钩子。`GenerationHooks.beforeRequest(request, api, context)` 的类型注释是 "Before every request attempt, including recovery"：每一次请求尝试之前都调用，包括失败后的重试和崩溃恢复后的重新请求。它拿到即将发出的消息列表，可以返回一份修改过的列表，只用于这一次请求。

所以 `beforeRequest` 是一个"每个模型回合、每次尝试"都会触发的挂点。上面的第一轮里它被调用了两次，第二轮一次。要把它变成"每轮一次"，钩子必须能判断这次调用属于哪一轮，并且这一轮是否已经处理过。

## 2. 识别一轮

### 2.1 钩子能读到的东西

`beforeRequest` 的第二个参数 `api` 是 `HookApi`：

```ts
interface HookApi extends DocumentReader {   // DocumentReader = Pick<Session, "snapshot" | "snapshotAsOf">
	readonly taskId: TaskId;                   // 当前 generation 任务
	readonly conversationId: ConversationId;
	readonly models: Models;
	memo(name, context) / memo(name, candidate, context);
}
```

它能读文档，不能读条目。generation 任务的输入类型 `GenerationInput` 是 `Record<string, never>`，也带不进任何信息。直接问"本轮的用户条目是哪条"，在钩子里得不到答案。

`memo` 也解决不了这个问题。memo 属于任务，`api.memo` 记在当前 generation 任务上，用它去重只能做到"每个 generation 一次"，第一轮里的 generation 9 和 14 各有各的 memo。

### 2.2 LiveDoc 的两个字段

引擎的运行状态存在内置文档里，[第 4 篇](04-持久化执行.md)提到的 `pi.live` 就是 `LiveDoc`。钩子可以用 `api.snapshot(LiveDoc, api.conversationId, context)` 读到它。对话忙碌时，它有一个 `run` 字段：

```ts
run?: {
	taskId: TaskId;           // "the task that settles the run's inputs"
	inputs: SubmissionId[];
};
```

在两轮运行的三次请求里读这两个字段：

| 字段 | 第 1 轮第 1 次请求 | 第 1 轮第 2 次请求 | 第 2 轮 |
|---|---|---|---|
| `api.taskId` | 9 | 14 | 18 |
| `run.taskId` | 9 | 14 | 18 |
| `run.inputs[0]` | 8 | 8 | 17 |

`run.taskId` 的注释读起来像"这一轮的任务"，测出来它是此刻负责推进这一轮的那个任务，和 `api.taskId` 完全相同，每个模型回合都换。用它做检查点的键，第一轮会打两次快照，一轮里有十次工具调用就打十一次。`run.inputs[0]` 等于两次 `submit()` 返回的提交 ID，同一轮内不变，换一轮才变，这才是"这一轮"的标识。

两个字段的差别是"此刻"和"整轮"的差别。同一份文档里，`run.taskId` 和 `generation`、`tools` 这些字段一样描述此刻的进展，`run.inputs` 描述这一轮由什么触发。只看注释分不出来，M0 用断言把这个事实固定在测试里。

### 2.3 从提交到条目

检查点要对齐到对话里的条目，钩子拿到的是提交 ID，还差一步。输入类提交的记录在不同状态下的字段：

| 状态 | 含义 | `entry` |
|---|---|---|
| `queued` | 已接受，还没放进对话 | 无 |
| `placed` | 已放进对话，属于正在进行的运行 | 本轮的 `pi.user` 条目 |
| `done` | 已回答 | 本轮的 `pi.user` 条目，另有 `answer` 指向回答 |

钩子被调用时，触发本轮的提交已经是 `placed`，宿主用提交 ID 查到它的记录，就拿到了条目 ID。实验里第一轮结束后，提交 8 的记录里 `entry` 指向的条目，`kind` 正是 `pi.user`。

### 2.4 用最后一条消息判断

还有一个更简单的信号。三次请求的消息列表，最后一条的 `role` 依次是 `user`、`toolResult`、`user`：一轮的第一个模型回合由用户输入驱动，之后的回合由工具结果驱动。

这个信号有一个漏洞。`whenBusy: "steer"` 的输入会在一轮工具调用之后加入正在进行的运行（第 4 篇 4.2 节），那之后的请求同样以用户消息结尾，却不是新的一轮。它适合作为辅助判断，不能当作检查点的键。steer 加入后 `run.inputs[0]` 是否仍是最初那条提交，M0 没有测，Tether 在实现检查点时补这个用例。

### 2.5 以提交 ID 为键

`perRun` 检查点于是这样实现：

1. `beforeRequest` 读 `LiveDoc`，取 `run.inputs[0]`。
2. 用这个提交 ID 查 Tether 自己的应用存储，看这一轮是否已经有检查点。
3. 没有就打快照，记录 `(sessionId, submissionId, snapshotId)`；有就直接返回，不改请求。
4. 快照完成后，从提交记录取出 `entry`，填进检查点的 `entryId`。

键在崩溃恢复之后不变。钩子因为重试、因为恢复后重新请求、因为同一轮的第二个模型回合被再次调用，查到的都是同一条记录，所以不会重复打快照。崩溃发生在第 3 步快照完成之后、记录写入之前，会留下一个没有记录的快照目录，这由启动对账清理（第 6 篇 4.2 节）。

## 3. 自定义条目

### 3.1 data 与 model

条目的结构里，和可见性有关的是两个可选字段：

```ts
type EntryRecord = {
	kind: string;                    // 应用自定义的类型，如 tether.sandbox
	model?: readonly Message[];      // "Messages contributed to model context; absent for display or bookkeeping entries"
	data?: JsonValue;                // 给视图、扩展、记账逻辑用的 JSON
	// id、conversationId、head、edits、byTaskId
};
```

引擎组装一次请求时，从当前上下文的起点开始，按顺序取各条目的 `model` 消息拼成消息列表。没有 `model` 的条目不贡献任何消息，它只存在于对话记录里，客户端读得到，模型看不到。`data` 不进入模型的上下文。

### 3.2 实测

M0 依次提交两条 `write` 和一条输入：

| 提交 | `kind` | `data` | `model` |
|---|---|---|---|
| 1 | `tether.sandbox` | `{ state: "running" }` | 无 |
| 2 | `tether.note` | `{ reason: "reset" }` | `[{ role: "user", content: "工作区已重置" }]` |
| 3 | 输入 "go" | | |

三条按提交顺序出现在对话记录里。`beforeRequest` 看到的消息列表包含"工作区已重置"，不包含 `running` 或 `tether.sandbox` 的任何内容。

### 3.3 放入的时机

[第 4 篇](04-持久化执行.md)的 4.2 节讲过 `write` 的两种时机：只有 `kind` 和 `data` 的条目立即追加，即使对话正在运行；带 `model` 的条目要等下一个边界才放入，和 steer 一样。

pi 的文档没有说明为什么要等边界。模型 API 一侧的一条约束可以解释它：助手消息里的工具调用，后面必须紧跟对应的工具结果，Anthropic 等接口会拒绝在两者之间插入一条用户消息的请求。带 `model` 的条目如果在工具执行期间立即追加，下一次请求的消息列表就会在工具调用和工具结果之间夹着它。等到一组工具结果都写完再放入，消息列表才是合法的。不带 `model` 的条目不进入消息列表，所以可以随时追加。

### 3.4 Tether 的条目

| 条目 | 带不带 `model` | 用途 |
|---|---|---|
| `tether.sandbox` | 视情况 | 沙箱状态变化：创建、启动、停止、丢失。只给客户端时不带；停止或重建导致后台进程结束时带上说明（[第 5 篇](05-崩溃后的旧进程.md) 4.1 节） |
| `tether.checkpoint` | 不带 | 检查点创建，客户端用来画时间线 |
| `tether.note` | 带 | 环境与对话不一致时的说明：从较早的检查点恢复、工作区重置、因闲置被停止 |

这些条目和模型的回答在同一条提交线上，客户端订阅一个事件源就能按正确的顺序看到全部事件，崩溃后也不会丢（第 4 篇 2.3 节）。

## 4. 结论

在引擎内部做"每轮一次"的事，要先分清哪些状态描述此刻，哪些描述整轮。pi-durable 的 `beforeRequest` 按模型回合和请求尝试触发，`LiveDoc.run.taskId` 随模型回合变化，`api.memo` 属于单个 generation 任务；只有 `run.inputs[0]`，即触发这一轮的提交，在整轮里保持不变，并且崩溃恢复后不变。以它为键，再由提交记录解析出条目，检查点就能做到每轮恰好一次。

自定义条目的可见性由 `model` 字段决定，时机由引擎的边界决定。宿主要做的判断只有一个：这条事件模型需不需要知道。需要知道的写成带 `model` 的条目，接受它在下一个边界才生效；只给客户端看的不带 `model`，立即出现，不影响模型。

这两点在第二阶段自研引擎时都要保留下来：钩子要能拿到一个整轮不变、恢复后不变的运行标识，条目要支持模型可见与不可见两种写法以及对应的放入时机。
