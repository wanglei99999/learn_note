# 执行通道

harness 不进沙箱时，agent 的工具调用要跨进程、跨机器执行：模型在服务端决定"读这个文件""跑这条命令"，动作发生在沙箱里。连接两端的这一层叫执行通道。它的帧格式很简单，真正的工作在格式之外：远端的每个文件操作和命令，结果要和在本机执行一模一样；慢链路上，命令输出不能拖慢请求的回复；连接断开后，哪些状态还有效、哪些已经作废，要有明确的规则。

这篇笔记以 pi-env 为对象分析这三件事。pi-env 由两部分组成：沙箱里运行的 Rust 程序 `pi-env serve`（下文称 daemon），以及服务端进程里的客户端 `RemoteExecutionEnv`。两者之间只有一条字节流，可以是 `ssh` 的标准输入输出，也可以是 `docker exec -i` 的标准输入输出。文中引用的行为都来自 pi-env 1.3.0 的 `docs/protocol.md`、`docs/semantics.md` 和 `src/connection.ts`。

## 1. 接口

### 1.1 ExecutionEnv

pi-durable 的工具（`read`、`write`、`edit`、`bash`）只通过 `ExecutionEnv` 接口接触文件和进程。这个接口由两部分组成：`FileSystem` 有二十多个方法，覆盖读写、按偏移读二进制、截断、`flush`、重命名、目录分页、文件监听、临时文件；`Shell` 只有 `exec` 和 `cleanup`。所有方法都返回 `Result`，失败是一个带错误码的值，不抛异常。

接口上还有一个 `id` 字段：`id` 相同的两个环境看到的是同一套文件。本机所有的 `NodeExecutionEnv` 共用一个 `id`，每个容器或远程主机有自己的 `id`。`write` 和 `edit` 按 `(id, 路径)` 串行化对同一个文件的修改，所以 `id` 不只是一个标签，它决定了并发写入的互斥范围。Tether 给每个沙箱一个 `docker:<容器名>` 形式的 `id`。

引擎不知道一个 `ExecutionEnv` 背后是本机还是远端。这是执行通道能够替换的前提：同一个 `bash` 工具，换一个环境对象，命令就在另一台机器上执行。

### 1.2 客户端和 daemon 的分工

一个文件操作的语义分散在两端。`docs/semantics.md` 列出了分工：

| 由客户端负责 | 由 daemon 负责 |
|---|---|
| 路径解析（`~`、`file://`、相对 `cwd` 的路径） | 系统调用 |
| 每个方法的取消检查点 | 进程的创建、等待和终止 |
| 错误码映射（`ENOENT` → `not_found`） | 命令输出的解码（按流分别做 UTF-8 解码） |
| `writeFile` 按 512 KiB 分块写、每块之前检查取消 | 超量输出写入溢出文件 |
| 超时校验，以及多个结果同时出现时的优先级 | 文件监听（快照比对加原生事件） |

原则是：需要知道远端文件系统状态的事放在 daemon，纯粹的计算和策略放在客户端。路径解析放在客户端，是因为它只依赖远端的 home 目录和路径规则，这两样在握手时就拿到了；文件监听放在 daemon，是因为 inotify 只能在文件所在的机器上用。

参照物是 pi-durable 的 `NodeExecutionEnv`：`RemoteExecutionEnv` 在远端执行的结果，必须和 `NodeExecutionEnv` 在那台机器上本地执行的结果相同，只允许错误消息的措辞不同。这条要求由两套测试保证：pi-durable 的环境一致性测试，以及一套随机操作序列的差分测试，把同样的操作分别交给两个实现，比较结果。

## 2. 帧协议

### 2.1 同步行

客户端启动 daemon 的命令是 `pi-env serve --token <hex>`，token 是每次启动时随机生成的 16 字节。daemon 的第一行输出是 `PI-ENV <token>\n`。客户端丢弃这一行之前收到的所有内容，之后标准输出上只有帧。

这一步处理的是 shell 启动文件的干扰。通过 `ssh` 启动时，远端的 `.bashrc` 可能打印欢迎信息，这些字节混在 daemon 的输出前面。用一个只有本次启动才知道的 token 做分界，客户端就能准确找到帧开始的位置。

### 2.2 帧格式

两个方向的帧格式相同，整数都是大端序：

```text
u32 length      之后的字节数
u8  type
u32 id          请求 ID；不属于任何请求的帧为 0
u32 jsonLength
json            UTF-8 JSON 对象
bytes           原始负载，长度为 length - 9 - jsonLength
```

帧类型有六种：请求、结果、错误、事件、取消、心跳。JSON 承载操作名和参数，文件内容和命令输出放在原始负载里，不做 base64 编码。

以 `bash` 工具执行 `npm test` 为例，客户端发出的请求帧，JSON 部分是 `{"command":"npm test","cwd":"/workspace","inheritEnv":true,"op":"exec"}`，71 字节，没有负载。`length` 字段等于 1 + 4 + 4 + 71 = 80，整帧 84 字节。命令运行期间，daemon 不断发回类型为"事件"、ID 相同的帧，JSON 是 `{"kind":"output","stream":"stdout"}`，负载是解码后的输出文本。命令结束时发一个"结果"帧，JSON 是 `{"exitCode":0}`，这个请求就此完成。

一帧最大 16 MiB，更大的文件由客户端拆成多个请求。JSON 解析失败的请求得到 `EINVAL` 错误；帧格式本身出错，连接直接结束，因为之后的字节已经无法可靠地切分。

### 2.3 取消

取消帧只指定一个请求 ID。daemon 在执行请求之前先登记它，所以紧跟在请求后面发出的取消不会丢失。`exec` 收到取消后杀掉命令的进程组，以 `aborted` 结束；`listFiles` 和 `scanLines` 在两个数据块之间停下；其他文件操作耗时很短，照常完成。

取消帧还有一个 `{ mode: "kill" }` 变体：杀掉进程但不算作取消，命令以被杀进程的退出状态结束。`cleanup()` 用的就是这种方式，被 `SIGKILL` 杀掉的命令报告退出码 128 + 9 = 137。

## 3. 慢链路

### 3.1 回复优先于输出

harness 不进沙箱，意味着每个工具调用都要跨一次网络。链路慢的时候，最怕一个命令刷出的大量输出把其他请求的回复堵在后面。

daemon 对发送顺序做了规定：结果、错误、心跳和文件监听事件，排在已经排队的命令输出前面；负载超过 64 KiB 的结果排在命令输出后面。也就是说，链路慢时被推迟的是大块数据，小的回复不受影响。`npm test` 正在刷几 MB 的日志时，同时发出的一个 `lstat` 请求照样能很快拿到结果。

### 3.2 输出窗口

`bash` 工具不需要命令的全部输出。模型只看输出的末尾，pi-durable 每 100 ms 才把输出提交一次。对远端来说，传输模型永远不会看到的那部分输出纯属浪费。

`exec` 请求可以带一个 `window` 参数：`{ maxBytes, maxLines, minIntervalMs, bytesPerSecond }`，描述调用方保留多少末尾、多久采样一次。daemon 据此合并输出，按调用方的提交节奏发送，每个命令最多只有一个输出帧在排队等待发送。超出窗口、调用方反正会丢弃的输出，daemon 不再发送，而是在下一个事件里附上 `skipped { bytes, newlines, endsWithNewline }`，告诉客户端跳过了多少字节、多少行。客户端用这三个数就能维护正确的行号和截断提示，不需要拿到原文。

没有窗口的命令，未发送的输出超过 4 MiB 时，daemon 暂停读取命令的输出管道，命令写满管道后会阻塞。效果和本地执行时下游读得慢一样，输出不会无限堆积在 daemon 的内存里。

### 3.3 溢出文件

输出超过 `spill.afterBytes` 或 `spill.afterLines` 时，daemon 把完整的原始输出写进远端一个新建临时目录下的 `pi-output-<uuid>.log`，结果里带上 `spillPath`。模型拿到的是末尾的一段，加上这个文件路径；需要时再用 `read` 工具去读完整日志。完整输出留在它产生的那台机器上，只在需要时才跨网络传输。

## 4. 连接与所有权

### 4.1 心跳和退出条件

两端每 5 秒发一次心跳。daemon 在两种情况下退出：标准输入结束，或者 30 秒没收到任何字节。退出前它杀掉自己启动的所有进程组。

两个条件对应两类故障。服务端进程崩溃，操作系统会关闭它持有的管道，`docker exec` 或 `ssh` 客户端随之退出，daemon 读到标准输入结束，立刻清理。连接卡住而没有断开，例如网络分区、`ssh` 客户端被挂起，daemon 收不到结束信号，要等 30 秒的静默期满才退出。在这 30 秒里，旧命令继续在沙箱里运行。[崩溃后的旧进程](05-崩溃后的旧进程.md)一篇专门处理这个窗口。

退出时杀掉所有进程组还有一个连带后果。agent 在 `bash` 里用 `npm run dev &` 启动的开发服务器，和启动它的命令在同一个进程组里（非交互的 bash 不做作业控制，后台任务不会另开进程组），daemon 退出时会被一起杀掉。连接一断，后台服务就没有了。

### 4.2 句柄属于 daemon

`open`、`opendir` 返回的句柄只在打开它的那个 daemon 里有效。连接断开后，客户端在下一次请求时自动启动一个新的 daemon，但旧句柄不会迁移过去。客户端给每个 daemon 编一个会话号，带着句柄的请求只发给打开句柄的那个会话；会话已经换了，请求直接失败，返回 `{ code: "unknown", lost: true }`，不会被新 daemon 误收。

在途的请求在连接断开时也以 `lost` 失败。对读操作，重试就行；对写操作，结果是未知的：写可能已经完成，也可能没有。`Connection` 的源码注释写的是"for mutations their outcome is then unknown"。执行通道本身不解决这个问题，它交给上层：pi-durable 对没有声明 `replay: "safe"` 的工具不做重试，给模型一个"中断"的结果，由模型决定怎么处理。

文件监听是唯一会被自动恢复的长期请求。新 daemon 启动后，客户端重新建立监听，并报告一次 `overflow`，表示"这段时间可能漏掉了变化，请重新扫描"。它不假装监听从未中断。

### 4.3 自动重启的插入点

`Connection` 的启动命令可以是一个函数，每次（重新）启动 daemon 之前调用一次，返回本次要执行的命令行。设计这个口子的本意是在启动前先探测远端系统、部署 daemon 二进制；Tether 用它在新 daemon 启动之前做隔离：把这次连接的 epoch 加一，清理上一个 epoch 留下的进程，再返回 `docker exec` 的命令行。整个过程不需要修改 `Connection` 的代码。

## 5. 命令的执行语义

daemon 里的 `exec` 遵循几条固定规则（`docs/semantics.md`）：

- 字符串命令通过 shell 执行，依次尝试 `/bin/bash`、`which bash`、`sh`；数组命令直接执行程序，参数不经过 shell 解析。
- 每个命令在一个新的会话里运行，信号处理恢复默认，信号掩码清空。超时、取消和 `cleanup()` 都用 `SIGKILL` 杀掉整个进程组。
- 进程退出后，继续收集输出，直到两个管道都关闭，或者 100 ms 内没有新输出；命令结束时关闭管道，即使有子孙进程还持有它们。
- 被信号杀死的进程报告 128 加信号编号。
- 环境变量：默认继承 daemon 的环境，再叠加 `shellEnv` 和请求里的 `env`；关闭 `inheritEnv` 时只用请求里的 `env`。

第二条决定了隔离要怎么做。每个命令单独开会话，所以按 daemon 的会话或进程组去杀，杀不到它启动的命令。Tether 的 Docker 后端选择在新 daemon 启动前，在容器里执行 `kill -KILL -1`，杀掉除 PID 1 和调用者以外的所有进程。这依赖一个前提：一个容器同一时刻只有一条连接。

最后一条和凭据有关。daemon 运行在沙箱里，它的环境变量是沙箱的环境变量，服务端的 API key 不会经过这条通道。只要服务端不把密钥放进请求的 `env`，模型写出的命令就读不到它们。

## 6. 结论

执行通道的协议部分只有一页：一个同步行，一种帧格式，六种帧类型。分量在三条规则上：远端结果与本地执行一致，并由差分测试保证；慢链路上回复优先、输出按调用方的需要裁剪；连接断开后，句柄和在途写操作明确作废，交由上层决定要不要重试。

这层能不能替换成别的实现，取决于新实现是否守住同样的三条规则，而不取决于它用什么帧格式。E2B 沙箱里的 `envd`、CubeSandbox 的 guest agent 承担的是同一个角色；Tether 第二阶段自己写的 daemon，也要跑同一套一致性测试和差分测试，才算替换成功。
