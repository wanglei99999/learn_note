# 沙箱后端

agent 写出的命令要在一个隔离的环境里执行，这个环境由沙箱后端提供。常见的选择有三类：普通容器（Docker 默认的 runc）、用户态内核（gVisor）、轻量虚拟机（Firecracker、CubeSandbox 用的 RustVMM）。它们对外的样子差不多，都是"一个能跑命令、有自己文件系统的地方"，区别在于沙箱里的代码和宿主机内核之间隔着什么。

容器隔着的是同一个内核上的 namespace、cgroup 和 seccomp 过滤；gVisor 隔着一个用 Go 写的、在用户态重新实现的内核；microVM 隔着一个独立的 guest 内核和硬件虚拟化。隔得越厚，沙箱里的代码越难影响宿主机；同时系统调用的代价、启动的速度、能不能保存内存状态，都跟着变化。这篇笔记按这三层分析机制和代价，最后说明 Tether 的取舍。文中的性能数字分两种：引用的是厂商公布的数据，会注明出处；没有实测过的不给数字。

## 1. 共享内核的攻击面

沙箱要防的是沙箱里的代码影响到沙箱外面。对 agent 来说，威胁来自两个方向：模型自己犯错（删掉不该删的目录、把磁盘写满、起一个死循环），以及模型被提示词注入后执行了恶意命令，比如它读到的某个网页或某个文件里藏着指令。

普通容器里的进程直接向宿主机内核发系统调用。namespace 让它看不到别的进程和文件，cgroup 限制它能用多少资源，但它和宿主机上的所有进程共用同一个内核。内核里任何一个可被利用的漏洞，都可能让容器里的代码突破隔离。所以容器隔离的强度，最终取决于宿主机内核暴露给容器的那部分接口有多大、有没有漏洞。

后面两类后端的思路都是缩小这个接口：gVisor 让绝大多数系统调用不到达宿主机内核，microVM 让沙箱有自己的内核，只通过很少几个虚拟设备和宿主机交互。

## 2. 普通容器

### 2.1 四层机制

Docker 默认的 runc 运行时把四种内核机制叠在一起：

- **namespace** 隔离视图：进程号、挂载点、网络、主机名、用户、IPC 各有一份。容器里的 `ps` 只看得到容器里的进程。
- **cgroup** 限制资源：CPU 份额、内存上限、进程数、IO。内存超限时内核在容器内部触发 OOM，不影响宿主机上的其他进程。
- **capability** 拆分 root 权限：容器里的 root 默认被去掉了一部分能力，例如 `CAP_SYS_PTRACE`，所以不能追踪任意进程。
- **seccomp** 过滤系统调用：默认配置是一个白名单，不在名单上的调用一律拒绝。被挡掉的调用里有 `bpf`、`reboot`、`add_key`，以及修改系统时钟的调用。Docker 文档给出的理由大多是这些接口没有被 namespace 隔离：内核的密钥环、系统时间都是全机共享的。

### 2.2 对 agent 的意义

对单用户、内网使用的 agent，主要威胁是模型误操作，四层机制已经够用。Tether 第一阶段给每个容器配置 CPU、内存和进程数上限，网络默认可选关闭（`network: "none"`）或只允许出站。磁盘配额 Docker 本身不直接提供，工作区放在宿主机目录里时，要靠宿主机文件系统的配额或者定期检查来限制。

普通容器的优势在于没有额外开销：系统调用直接进内核，启动一个容器是创建几个 namespace 和一个 overlay 挂载。它的局限是快照只能做到文件系统，没有办法保存正在运行的进程（见[沙箱检查点](06-沙箱检查点.md)）。

## 3. 用户态内核：gVisor

### 3.1 Sentry 和拦截方式

gVisor 的核心是 Sentry，一个用 Go 写的用户态内核，重新实现了 Linux 的系统调用接口。容器里的进程发出的系统调用，被拦截后交给 Sentry 处理，Sentry 自己再用一个很小的系统调用集合向宿主机内核请求资源。宿主机内核暴露给沙箱的接口，从几百个系统调用缩小到 Sentry 需要的那一小部分。

拦截的方式叫 platform。默认的 systrap 用 seccomp 的 `SECCOMP_RET_TRAP`：沙箱进程一发系统调用，内核就向它发送 `SIGSYS`，控制权转到 gVisor。2023 年中 systrap 取代 ptrace 成为默认值，ptrace 方式已经不再支持。在裸金属机器上还可以用 KVM platform，借助硬件虚拟化做地址空间隔离。

文件访问原来通过一个单独的 Gofer 进程代理。2023 年起 runsc 默认开启 directfs，Sentry 可以直接访问容器的文件系统，省掉了每次文件操作到 Gofer 的往返。

### 3.2 兼容性与代价

Sentry 没有实现全部系统调用，冷门的调用会失败。普通的编码任务（git、node、python、编译器）一般没有问题，依赖特殊内核特性的程序可能跑不起来。

代价在系统调用密集的操作上。每次拦截都要经过一次信号和上下文切换，`npm install` 这类要创建大量小文件的操作会明显变慢。具体慢多少取决于负载和 platform，这里不给数字，留给 Tether 的实测。

对使用方来说，gVisor 的接口和 Docker 完全一样：它提供一个叫 `runsc` 的 OCI 运行时，`docker run --runtime=runsc` 就能切换。Tether 的 Docker 后端因此不需要改代码，只多一个配置项。Google 的 App Engine、Cloud Run、Cloud Functions 都用 gVisor 隔离用户代码。

## 4. 轻量虚拟机

### 4.1 Firecracker

Firecracker 是 AWS 为 Lambda 和 Fargate 开发的虚拟机监视器（VMM），用 Rust 写成，运行在 KVM 之上。它刻意只模拟极少的设备：virtio-net、virtio-block、virtio-vsock、串口，以及一个只用来让 guest 重启的最小键盘控制器。没有 BIOS，直接引导 Linux 内核。设备越少，VMM 里可被攻击的代码就越少。VMM 进程本身还运行在 seccomp 过滤和一个叫 jailer 的受限环境里，即使 guest 突破了 VMM，拿到的也只是一个权限很低的宿主进程。

官方公布的数据是：一个 microVM 最快 125 ms 启动，每个 VM 的内存开销小于 5 MiB，单台主机每秒可以创建最多 150 个 microVM。E2B 的沙箱就是 Firecracker microVM，沙箱里的 `envd` 负责执行命令和读写文件。

CubeSandbox 用的是另一个基于 RustVMM 的实现，思路相同。它公布的数据是冷启动 60 ms 以内，单实例内存开销小于 5 MB；这些是腾讯在自己的裸金属环境上测的，还没有独立的测评。

### 4.2 虚拟机带来的能力

guest 有自己的内核，宿主机内核暴露给沙箱的只有 KVM 接口和那几个虚拟设备。沙箱里的代码即使利用了 guest 内核的漏洞，拿到的也只是 guest 的 root。

虚拟机还能保存内存。暂停一个 microVM，可以把它的内存和磁盘一起保存下来，恢复后进程接着运行，agent 启动的开发服务器、跑了一半的测试都还在。E2B 的暂停就是这样；CubeSandbox 在此之上做了增量的内存快照，只保存两次快照之间写过的页（见[沙箱检查点](06-沙箱检查点.md)）。这是容器和 gVisor 做不到的。

### 4.3 硬件要求

microVM 必须运行在有 KVM 的 Linux 上：物理机，或者开启了嵌套虚拟化的云主机。Windows 10 上的 WSL2 不支持嵌套虚拟化，开发机上跑不了。CubeSandbox 提供了一个变通办法：在普通的 x86_64 云主机上安装它的 PVM 内核，不需要宿主机暴露 `/dev/kvm`。它的部署要求还包括 glibc 2.31 以上、`/data/cubelet` 必须是 XFS（快照依赖 reflink）、至少 50 GB 磁盘、4 核 8 GB 内存。

## 5. 对比

| | 普通容器（runc） | gVisor（runsc） | microVM（Firecracker、CubeSandbox） |
|---|---|---|---|
| 沙箱与宿主内核之间 | namespace、cgroup、capability、seccomp | 用户态内核 Sentry | 独立的 guest 内核 + KVM |
| 宿主内核暴露的接口 | seccomp 白名单内的系统调用 | Sentry 需要的少量系统调用 | KVM 接口和几个虚拟设备 |
| 系统调用开销 | 无额外开销 | 每次拦截一次信号和切换 | guest 内核内处理，退出到 VMM 才有开销 |
| 启动 | 创建 namespace 和 overlay 挂载 | 同容器，多启动一个 Sentry | 官方数据 125 ms（Firecracker）、60 ms 以内（CubeSandbox） |
| 快照 | 只有文件系统 | 只有文件系统 | 文件系统 + 内存 |
| 兼容性 | 完整 | 部分冷门系统调用不支持 | 完整（guest 是真的 Linux） |
| 硬件要求 | 任意 Linux | 任意 Linux，KVM platform 需要裸金属 | KVM 或 PVM |

## 6. Tether 的取舍

Tether 第一阶段是单用户、内网部署，主要威胁是模型误操作，选择普通容器：

- 默认 runc，每个容器配置资源上限和网络策略。
- 需要更强隔离时切换到 `runsc`，代码不变；第一阶段的混沌测试在 runc 和 gVisor 上各跑一遍，顺带测出 gVisor 在 `npm install` 这类负载上的实际代价。
- 不保存内存。检查点只有文件系统，恢复后后台进程需要重新启动，并写一条说明告诉模型。

第二阶段自己实现一个 Firecracker 后端，它和 Docker 后端实现同一个 `SandboxProvider` 接口，能力表里多出"保存内存"一项。到那时可以在同一套测试上直接比较三种后端的隔离强度、启动时间和工具调用延迟，用实测数据代替这里引用的厂商数据。

## 7. 结论

沙箱后端的差别在于沙箱里的代码和宿主机内核之间隔着什么：普通容器共享内核，靠过滤缩小接口；gVisor 在用户态重新实现内核，让大部分系统调用不到达宿主机；microVM 给沙箱一个独立的内核，只留下几个虚拟设备作为接口。隔得越厚，越能抵御内核漏洞，也越能保存完整的运行状态，代价是系统调用开销、兼容性和硬件要求。

选哪一种取决于三个条件：威胁来自模型的误操作还是可能被注入的恶意代码，是否需要在暂停和恢复之间保住正在运行的进程，以及部署环境有没有 KVM。只防误操作、不需要保存进程、没有 KVM 时，普通容器加资源限制就够了；要运行不可信的多租户代码，或者要保住进程，就需要 microVM。
