# 崩溃后的旧进程

服务端崩溃重启之后，持久化引擎会把执行到一半的命令报告为"中断"，模型据此决定下一步。这个报告有一个隐含的前提：被中断的命令确实已经停了。在 harness 不进沙箱的架构里，这个前提不一定成立。命令运行在沙箱里，由沙箱里的 daemon 启动，服务端进程没了，daemon 和命令可能还活着。

于是会出现两个所有者同时作用于同一个工作区：旧 daemon 启动的命令还在写文件，新连接上模型重新发起的命令也在写。解决办法是新连接在开始工作之前，主动让旧连接留下的一切失效，而不是等旧 daemon 自己发现连接断了。这篇笔记分析这个窗口从哪里来，Tether 怎样用 epoch 隔离把它关掉，以及隔离带来的代价。文中引用的 pi-env 行为来自 1.3.0 的 `docs/protocol.md` 和 `docs/semantics.md`，窗口的长度和隔离的效果在 Tether 的 M0 实验里实测过（第 5 节），测试机是 2 核 2 GiB 的 Ubuntu 24.04，Docker 29。

## 1. 窗口的来源

### 1.1 daemon 的两个退出条件

pi-env 的 daemon 在两种情况下退出：标准输入结束，或者 30 秒没收到任何字节。退出前杀掉它启动的所有进程组。

这两个条件对应两类故障：

| 故障 | daemon 观察到的 | 旧命令停止的时间 |
|---|---|---|
| 服务端进程崩溃或被杀 | 管道关闭，`docker exec` 客户端退出，标准输入结束 | 立即 |
| 连接卡住而没有断开：网络分区、客户端进程被挂起、代理没有转发连接关闭 | 什么都收不到，也没有结束信号 | 30 秒静默期满之后 |

第一类最常见。进程被 `kill -9` 时，操作系统关闭它持有的所有文件描述符，`docker exec` 或 `ssh` 客户端读到管道关闭后退出，容器里的 daemon 随即读到标准输入结束。这种情况下窗口几乎为零。

第二类才会留下窗口。共同点是连接的一端已经不在了，但关闭的消息没有传到 daemon。本地 Docker 后端也能进入这种状态：`docker exec` 客户端进程被 `SIGSTOP` 挂起，或者 Docker 守护进程卡住，管道既不关闭也不传数据。远程后端更容易遇到：管道中间隔着 WebSocket 桥和后端的代理，服务端这一侧的连接断了，代理不一定马上关闭它通向沙箱的那一段。

### 1.2 一个具体的时间线

下面是一个示意的时间线。设 Tether 接的是远程后端，服务端通过代理连到沙箱里的 WebSocket 桥，桥再把字节转给 daemon 的标准输入。服务端进程在 t = 0 时崩溃，代理没有把连接关闭传给沙箱里的桥，桥也就一直不关闭 daemon 的标准输入；t = 10 秒时新进程启动完成：

- t = 0：服务端正在执行 `bash: npm install`，已经运行了 40 秒。服务端进程崩溃，daemon 从这一刻起收不到任何字节。
- t = 10：新服务端打开存储，pi-durable 看到这个未完成的 `bash` 任务，它不是 replay-safe，于是给模型一个 `interrupted` 结果。
- t = 12：模型决定重新执行 `npm install`。新服务端经由一条新的代理连接启动一个新 daemon，新命令开始运行。
- t = 12 到 30：旧 daemon 还在等心跳，旧的 `npm install` 继续运行。两个 `npm install` 同时写 `node_modules`。
- t = 30：旧 daemon 的静默期满，杀掉旧命令。`node_modules` 里留下的是两个进程交错写入的结果。

18 秒的重叠足以让 `node_modules` 处于不一致的状态，而新的 `npm install` 结束时报告成功，模型没有理由怀疑。

## 2. 两个所有者

### 2.1 引擎的报告为什么不够

pi-durable 在 t = 10 时做的事是对的：它不知道旧命令的状态，所以不重放，如实报告中断。但"中断"这个词让模型以为命令已经停了。模型看到的世界和沙箱里实际发生的事在 t = 10 到 30 之间是不一致的。

这个问题不能交给模型处理。模型无从知道旧 daemon 还活着；就算在中断结果里加一句"旧命令可能还在运行"，模型也只能选择等待或者冒险，两种都不是好的默认行为。问题要在执行层解决：把"中断"从一个报告变成一个事实，在模型的下一个命令开始之前，保证旧命令已经停了。

### 2.2 分布式系统里的同一个问题

这是分布式锁里的经典问题。一个持有租约的客户端因为 GC 停顿或网络分区失联，租约过期后锁被交给第二个客户端；第一个客户端恢复后，并不知道自己已经失去了锁，继续写存储。Martin Kleppmann 在《How to do distributed locking》（2016）里给出的解法是 fencing token：每次发放锁时附带一个单调递增的编号，存储拒绝编号比已见过的最大编号小的写入。

Tether 的情况比这简单，也更麻烦。简单在于只有一个服务端进程在写，epoch 不需要分布式共识，存在应用数据库里就行。麻烦在于"存储"是沙箱里的文件系统和进程，没有办法让 `npm` 在写文件时检查一个编号。被动地拒绝旧写入做不到，只能主动地在新连接开始之前把旧的写入者全部杀掉。

## 3. epoch 隔离

### 3.1 编号与记录

`sandbox_bindings` 表里每个沙箱有一个 `epoch` 字段，服务端每次（重新）连接这个沙箱时加一。启动 daemon 时，Tether 不直接执行 `pi-env serve`，而是执行一个包装脚本 `launch.sh <epoch>`：它在 `/run/tether/daemons/` 下写一个 `<epoch>.<PID>` 的记录文件，然后 `exec` 成 daemon，保持 PID 不变。记录文件用来观察和断言当前是哪个 epoch，隔离本身不依赖它。

### 3.2 插入点

pi-env 的客户端 `Connection` 在连接丢失后，会在下一次请求时自动启动一个新 daemon。这个自动重启如果不加控制，就会绕过隔离：新 daemon 启动了，旧的还在。

`Connection` 的启动命令可以是一个函数，每次启动 daemon 之前调用一次，返回本次的命令行。Tether 在这个函数里依次做三件事：把 epoch 加一并写回数据库；在容器里执行隔离，清理上一个 epoch 留下的进程；返回 `docker exec -i <容器> /opt/tether/launch.sh <新 epoch>`。隔离完成之前，函数不返回，新 daemon 就不会启动，请求也就不会到达沙箱。整个过程不需要修改 `Connection` 的代码。

### 3.3 杀到哪一层

隔离要杀掉旧 daemon 以及它启动的所有命令。按 daemon 的会话或进程组去杀是行不通的：daemon 给每个命令单独开一个新会话（`docs/semantics.md`："Each command gets a new session"），命令的进程组和 daemon 的进程组没有关系，按 daemon 杀不到它们。

按进程树去找也不可靠。命令可以 fork 出子进程再退出，子进程被 PID 1 收养，和 daemon 之间不再有父子关系。

Tether 的 Docker 后端用的是 `kill -KILL -1`。从容器里执行时，它向调用者能发送信号的所有进程发送 `SIGKILL`，PID 1 和调用者自己除外。容器的 PID 1 是一个 `sleep infinity`，不受影响；旧 daemon、它启动的命令、命令留下的孤儿进程，全部被杀。

这个做法依赖一个前提：一个容器同一时刻只服务一条连接。Tether 一个会话一个容器，一个会话同一时刻只有一个服务端进程在操作它，前提成立。远程后端如果做不到"一容器一连接"，就要退回按记录文件里的 PID 逐个清理它的子进程组，并接受孤儿进程可能漏网。

`kill -1` 的范围是调用者所在的 PID 命名空间。容器有自己的命名空间时，这个范围就是容器；容器以 `--pid=host` 启动时，范围变成整台宿主机，`kill -KILL -1` 会杀掉 sshd 在内的所有进程。所以隔离之前要做两道检查。宿主侧用 `docker inspect` 确认容器的 `HostConfig.PidMode` 为空，并在容器里读 `/proc/1/comm`，确认 PID 1 是容器自己的 init（`sleep`）。容器里的隔离脚本在执行 kill 之前再读一次 `/proc/1/comm`，宿主侧的检查即使有 bug，这一道也会让脚本退出。验证这两道检查时，测试只对 `--pid=host` 容器调用检查函数，不调用隔离本身：检查一旦失效，测试自己就会杀掉整台测试机的进程。

### 3.4 隔离完成才算重连成功

只有隔离脚本执行成功，这次重连才算成功。隔离失败（例如容器已经不存在），启动命令的函数抛出错误，`Connection` 把这次启动记为失败，这次工具调用返回错误结果；下一次请求会重新尝试，再走一遍隔离。不允许出现"隔离没做完，新 daemon 先启动了"的状态。

## 4. 代价

### 4.1 后台服务随连接一起结束

agent 经常用 `npm run dev &` 启动开发服务器，之后用 `curl` 去测它。在 pi-env 的模型里，这个后台进程和启动它的 `bash` 命令在同一个进程组里：非交互的 bash 不做作业控制，后台任务不会另开进程组。daemon 退出时杀掉它启动的所有进程组，开发服务器就跟着没了。epoch 隔离用 `kill -1`，同样会杀掉它。

所以连接一断，无论是崩溃、卡住还是正常的服务端重启，沙箱里的后台服务都会结束。这个结果本身可以接受，不能接受的是模型不知道：它会接着用 `curl localhost:3000` 去测一个已经不存在的服务，然后把连接失败当成代码的问题去修。Tether 在每次隔离之后，往会话里写一条模型可见的 `tether.sandbox` 条目，说明"与沙箱的连接已重建，此前启动的后台进程已结束"。

### 4.2 一次额外的往返

每次建立连接多了三次 docker CLI 调用：`docker inspect` 和读 `/proc/1/comm` 的 `docker exec` 用于检查，再一次 `docker exec` 执行隔离脚本。在测试机上连续测 10 次，一次隔离耗时 253 到 272 ms，中位数 264 ms，每次 CLI 调用约 90 ms，主要花在启动 docker 客户端和与守护进程的往返上。连接只在服务端启动后的第一次工具调用、以及连接丢失之后建立，正常运行时复用同一条连接，这个开销不出现在每次工具调用上。

## 5. 验证

### 5.1 窗口的实际长度

M0 的 Task 5 用一个子进程持有到容器的连接，让 daemon 执行 `sleep 300; echo late > late.txt`，然后对子进程发信号，在 1 秒、10 秒、40 秒时检查容器里的旧 daemon 和旧命令：

| 信号 | 对应的故障 | 1 秒 | 10 秒 | 40 秒 |
|---|---|---|---|---|
| `SIGKILL` | 服务端进程崩溃 | 都已结束 | 都已结束 | 都已结束 |
| `SIGSTOP` | 连接卡住，管道没有关闭 | 都在运行 | 都在运行 | 都已结束 |

结果与 1.1 节的分析一致。`SIGKILL` 之后子进程持有的管道被关闭，它启动的 `docker exec` 客户端随之退出，daemon 读到标准输入结束，1 秒内旧命令就没了。`SIGSTOP` 只挂起子进程本身，它的子进程 `docker exec` 客户端仍然活着，管道保持打开，daemon 只能等 30 秒静默期满。

持久化引擎那一侧在 Task 4 里验证过：让 `bash` 执行 `sleep 5` 期间 `SIGKILL` 掉持有 Harness 的进程，重新打开存储后，这次调用得到 `Tool bash was interrupted and may have partially run` 的错误结果，命令没有被重新执行，模型只被调用了一次（中断之后的那一轮）。

### 5.2 隔离的效果

把持有连接的子进程 `SIGSTOP`，让旧命令处在"还在运行"的状态，立即用启动命令函数建立新连接（epoch 2）：

- 新连接上的命令正常完成；
- 容器里找不到旧的 `sleep 300`，不用等 30 秒；
- `/run/tether/daemons/` 下只剩 `2.<PID>` 一条记录；
- 35 秒后，旧命令本该写出的 `late.txt` 不存在，新连接仍然可用，旧 daemon 的静默超时没有影响新连接。

最后一条同时说明 `Connection` 确实在每次启动 daemon 之前调用启动命令函数，3.2 节的插入点成立。

### 5.3 判断进程是否存活的陷阱

实验里第一次判断命令是否在运行时，用的是 `docker exec <容器> sh -c "pgrep -f 'sleep 5'"`。`pgrep -f` 匹配完整的命令行，而执行它的那个 `sh` 的命令行里正好也有 `sleep 5`，于是它总能匹配到自己，测试在命令真正开始之前就以为它已经在跑。改成 `pgrep -f '[s]leep 5'`：正则 `[s]leep` 能匹配 `sleep`，但 `sh` 命令行里的字面量是 `[s]leep`，匹配不上。或者让命令自己写一个标记文件，检查文件是否存在。以后的混沌测试也要用这两种写法。

## 6. 结论

崩溃后的旧进程问题，是同一个工作区在一段时间里有两个所有者。持久化引擎报告"中断"只解决了模型那一侧的信息，沙箱那一侧要靠执行层保证：新所有者开始工作之前，旧所有者的进程已经全部停止。

在文件系统和进程上做不到 fencing token 那样的被动拒绝，只能主动清理，所以隔离的可靠性取决于两个条件：能不能准确找到旧所有者的全部进程（Docker 上一容器一连接时，`kill -1` 可以），以及隔离能不能插在新 daemon 启动之前（pi-env 的启动命令函数可以）。M0 的实测确认了两个条件都满足，窗口从约 30 秒变成零，每次建立连接多花约 260 ms。代价是每次重连都会结束沙箱里的后台服务，这一点必须告诉模型；`kill -1` 的范围取决于 PID 命名空间，这一点必须在执行前检查。
