# 持久化执行

服务端 agent 的一次运行可能持续几十分钟，期间进程随时可能被重启：发布新版本、机器维护、内存溢出被杀。持久化执行要做到的是，进程重新打开存储之后，未完成的运行从断点继续，而且已经做过的事不会再做一遍。

这里的"不再做一遍"需要说准确。引擎能保证的是工具调用至多执行一次，不能保证恰好执行一次：一个命令跑到一半进程崩溃，引擎无法知道它在沙箱里产生了哪些效果，重跑可能重复副作用，不重跑又可能缺一步。持久化引擎的工作，是把这种不确定性变成一条模型看得见、持久保存的事实，交给模型或工具自己的幂等机制去处理。这篇笔记以 pi-durable 1.3.0 为对象，分析它的数据模型、工具调用的提交顺序和重放规则，以及提交请求的幂等性。

## 1. 先提交，再展示

### 1.1 一条提交线

pi-durable 的 `Harness` 是一份打开的存储，加上在它上面运行 agent 的机制。所有修改都经过同一条原子提交线，提交之前什么都不对外展示。UI 看到的每一个字，都是已经写进存储的内容。

这条规则决定了崩溃后的世界是什么样子：存储里有的，就是发生过的；客户端看到过的，存储里一定有。不会出现"用户在屏幕上看到了模型的回答，重启后回答消失了"这种情况。

### 1.2 流式输出的提交间隔

模型的流式回答和工具的运行输出不是每个 token 提交一次，那样写入量太大。默认每 100 ms 提交一次，可以通过 `settings.progress` 调整。崩溃最多丢掉最后 100 ms 的输出。存储在远端时可以放宽到 500 ms，用更大的丢失窗口换更少的写入。

存储后端有四种：内存、SQLite、JSONL 和 Cloudflare Durable Object。SQLite 用 WAL 模式加 `synchronous = NORMAL`：进程崩溃时已提交的数据都在，断电或宿主机故障时最新的一次提交可能丢失。一份存储同一时刻只能由一个进程打开，没有跨进程的锁。

## 2. 数据模型

### 2.1 条目、文档、任务

存储里有三类东西。

**条目**是对话记录里不可变的一条：用户消息 `pi.user`、模型回答 `pi.assistant`、工具结果 `pi.tool-result`、系统提示词的变化 `pi.system`，也可以是应用自定义的类型。模型看到的是最近一次重置之后的条目。

**文档**是和对话记录存在一起的、有类型的 JSON 状态，在提交里修改。引擎内置的几个文档记录了每个对话的运行状态：`pi.agent` 存这个对话用什么模型和工具，`pi.live` 存正在进行的生成和工具调用，`pi.inbox` 存排队的输入，`pi.usage` 存花费。

**任务**是一个持久化的状态机，每走一步保存一个检查点，重启后的进程从最后一个检查点继续。每个任务都有所有者：一个对话，或者另一个任务。

### 2.2 一次回答的任务结构

用户的一条输入被回答，在存储里是这样的结构：

```text
submit(input) → pi.user
  pi.generation → pi.system（仅当提示词或工具变化时）, pi.assistant（含工具调用）
    pi.tool × n → pi.tool-result × n   （归 generation 所有，generation 等待它们完成）
  pi.generation → pi.assistant（最终回答）→ submission done
```

每个模型回合是一个 `pi.generation` 任务，它拥有本轮所有的 `pi.tool` 任务，等它们全部结束，再把运行交给下一个 generation。一次运行就是从一条输入到最终回答之间的所有回合。

所有权关系决定了中断和崩溃怎么传播。中断一个任务时，先中断它拥有的工作，再执行它自己的中断处理，所以每个任务只需要撤销自己的效果。父任务只有在它拥有的子任务都结束后才算空闲。

### 2.3 一次提交里的原子性

`conversation.commit((tx) => ...)` 可以在同一次提交里追加条目、修改文档、创建任务，要么全部存下，要么全部不存。应用自己的状态也可以用 `defineDoc` 定义成文档，和对话记录一起提交。Tether 把沙箱状态变化、检查点、"工作区已重置"这类说明写成 `tether.*` 类型的条目，就是利用这一点：它们和模型的回答在同一条提交线上，先后顺序天然一致，崩溃后也不会丢。

## 3. 工具调用的提交顺序

### 3.1 意图先于执行

每个工具调用都是一个独立的持久化任务。引擎在调用 `execute()` 之前，先提交这次调用的意图：工具名、参数、它属于哪个 generation。然后才真正执行。

以一次 `bash` 调用为例，设 `npm test` 要跑 20 秒，进程在第 3 秒崩溃：

1. 意图已提交，存储里有一个状态为 `running` 的 `pi.tool` 任务。
2. 前 3 秒的输出每 100 ms 提交一次，存储里有约 2.9 秒到 3 秒的输出。
3. 进程崩溃，任务停在 `running`。

重新打开存储后，引擎看到这个未完成的任务，按工具声明的重放策略处理。

### 3.2 重放策略

工具可以声明 `replay: "safe"`。

- 声明了 `safe` 的工具，在重新打开后重新执行。
- 没有声明的工具（包括内置的 `bash`、`write`、`edit`）不重新执行。模型收到一个 `interrupted` 错误结果，里面带着崩溃前已经提交的输出。

上面的例子里，模型下一轮看到的是：`npm test` 被中断了，这是它前 3 秒打印的内容。要不要重跑，由模型根据这些信息决定。`npm test` 重跑没有坏处；如果被中断的是一次数据库迁移，模型可能先去查一下迁移执行到了哪一步。

默认不重放的理由是，引擎无法判断一个命令在崩溃前产生了哪些效果。`rm -rf build && npm run build` 中断在第一个 `&&` 之后，`build` 目录已经删了，新的还没生成；自动重跑碰巧没问题，换成 `git push` 或者调一个发邮件的接口就不一定了。所以默认行为是至多执行一次：执行过的不会再自动执行，没执行完的如实报告。

### 3.3 replay-safe 不等于幂等

声明 `replay: "safe"` 只是告诉引擎"重跑这个工具没关系"，引擎并不替工具做幂等。README 对嵌套调用的说明写得很直接：被崩溃打断、结果还没提交的嵌套调用，按它自己的重放策略处理，"所以一个有外部副作用的 replay-safe 工具，仍然需要它自己的幂等机制"。

一个调用外部支付接口的工具，如果要声明为 replay-safe，就要自己带上幂等键，比如用 `api.taskId` 作为支付请求的去重 ID，让支付服务在重复请求时返回第一次的结果。引擎提供的是稳定的任务 ID，幂等本身要由工具和外部服务配合完成。

### 3.4 嵌套调用的重连

一个工具可以通过 `api.executeTool()` 调用另一个工具，被调用的那个也是一个独立的任务，归调用方所有。每个嵌套调用有一个键，默认是它在调用方所有嵌套调用中的序号。

replay-safe 的调用方在崩溃后重跑时，只要按同样的顺序发起嵌套调用（或者传同样的键），拿回的就是之前已经发起的那些调用，已完成的直接拿结果，仍在运行的继续等待，不会重新开始。不是 replay-safe 的调用方在重启后不会重跑，它留下的未完成嵌套调用连同它们拥有的一切，在重新运行之前被放弃。

code mode 把这个机制用到了极致。模型写的 JavaScript 在 QuickJS 沙箱里确定性地运行：虚拟时钟、固定的随机种子、UTC 时区。脚本每拿到一个工具结果，结果先写进日志再交给脚本。重启后脚本从头再跑一遍，日志按同样的顺序把结果喂回去，脚本于是发起同样的调用、带同样的参数，按键接回原来的嵌套调用，然后从断点继续。如果重跑时脚本走了一条和上次不同的路径，或者沙箱的指纹、code mode 的版本变了，这次调用以错误结束，不会把结果错配到不同的调用上。

## 4. 提交请求的幂等

### 4.1 requestId

工具调用的问题出在服务端和沙箱之间；客户端和服务端之间有同样的问题。客户端发出一条消息，服务端处理后在返回响应前崩溃，客户端超时重试，同一条消息可能被提交两次，agent 就会把同一件事做两遍。

`submit()` 接受一个 `requestId`。带同样 `requestId` 的提交，返回已经存在的那个 submission，不会再提交一次。重启之后用同一个 `requestId` 重试，也能找到原来那个 submission。Tether 的 SDK 在每次发消息时自动生成 `requestId`，重试时复用同一个值。

### 4.2 忙碌时的输入

对话正在运行时提交的输入，进入对话的收件箱 `pi.inbox`，按 `whenBusy` 的取值处理：

- `followUp`（默认）：等当前运行回答完，作为下一轮运行的输入。
- `steer`：放在当前这一轮工具调用之后，加入正在进行的工作。
- `reject`：直接拒绝，抛出 `ConversationBusy`。

还有一种 `write` 类型的提交，只追加一个条目，不让模型做任何事。只有 `kind` 和 `data` 的 write 不改变模型看到的内容，所以即使在运行中间也立即追加，不排队；带了 `model` 字段、会被模型看到的 write，要等到下一个边界才放入，和 steer 一样。这条规则让 Tether 的两类说明有了不同的行为：沙箱状态这类只给客户端看的条目立即出现，"工作区已重置"这类要让模型知道的条目，在下一轮请求之前放入。

## 5. 错误的边界

pi-durable 把错误分成三类，各自影响的范围不同：

- **存储错误终止整个 Harness。** 触发错误的调用失败，之后的所有调用和等待都以 `SessionFailed` 失败，运行中的任务收到中断信号，Harness 自行关闭。不做重试，恢复的方式是重新打开存储。因为提交是原子的，重新打开时存储总是一致的。
- **无效的读取只让这一次调用失败。** 例如游标无效、对话不存在。这条豁免只适用于读取，提交过程中的任何错误仍然终止 Harness。
- **应用自己的代码只让它自己的单元失败。** 任务的某一步抛错，这个任务失败；工具抛错，模型拿到一个错误结果；钩子抛错，记录下来并跳过（`beforeTool` 抛错时阻止这次调用）；提交回调抛错，这次提交回滚。

第一条的含义是：存储出问题时，引擎选择立即停下，而不是带着不确定的状态继续运行。宿主程序监听 `harness.closed`，在失败原因是 `failed` 时重新打开存储。Tether 的服务端在这一点上照做，并且在重新打开之前先完成沙箱对账，保证恢复的工具调用拿到的是最新的沙箱状态。

## 6. 结论

持久化执行由三条规则构成：所有状态先提交再展示；工具调用先提交意图再执行；默认不重放执行到一半的工具，把中断和已提交的输出作为结果交给模型。三条规则合起来，保证的是至多一次，以及不确定性一定会被记录下来。

恰好一次只能在至多一次之上，由工具和外部服务自己的幂等机制补齐。一个工具能不能声明为 replay-safe，取决于两个条件：它的副作用是否只落在可以重建的地方（例如沙箱里的构建目录），以及它调用的外部服务是否接受一个稳定的去重键。两个条件都不满足的工具，应该保持默认，让模型在看到中断之后自己判断下一步。
