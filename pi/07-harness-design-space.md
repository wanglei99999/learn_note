# 07 — harness 的设计空间：一份可带走的坐标系

> 学习系列第 7 篇，与前面所有篇都不同。
>
> 01–06 讲的是**pi 怎么做的**：有文件名、有行号、跟着代码走。本篇讲的是**任何 agent harness 都要回答的问题**：不提 pi 的文件名，只留问题、答案空间和判据。
>
> 写它的理由：学 pi 的目的若是"以后看别的架构能更快看懂"，那么知识必须从 pi 身上剥下来。否则你看别的系统时，脑子里浮现的是某个具体函数名，而不是"这里有个选择要做"。
>
> **读法**：每一问给出「问题是什么 / pi 的答案 / 别的选择 / 判据」。pi 的答案只是一种答法，**知道它是选择而非唯一解，才叫看懂了**。需要具体实现时，各问末尾标了对应篇目。

## 第 1 章 harness 是什么

字面意思是马具。**马提供动力，马具让这份动力能拉动车。**

模型就是那匹马：

```text
模型：  tokens ──► tokens
        无状态、无副作用、一次性
```

给它 token，它吐 token。一次 API 调用结束，它就什么都不记得了；它碰不到文件、发不出请求、也不会自己再来一次。

**harness = 模型之外的一切**——把这个"文本补全函数"变成"能干活的东西"的全部外围装置。

### 1.1 一个常见的误解

学完一个以上下文为重心的 harness，很容易得出"agent 就是 context engineering"的结论。这个直觉有依据：**模型只有一个输入通道**，harness 干的所有事最终都必须翻译成"往上下文里放什么"。

```text
工具？      定义是 token，结果也是 token
记忆？      存的是 token
权限拦截？  拦截的效果是回去一条 blocked 的 toolResult，还是 token
```

从模型的视角看，整个世界确实就是一段上下文。

**但这等于说"编程就是决定内存里放什么字节"**——技术上成立，却把最重要的区分抹掉了。当 agent 执行一次文件写入时，**磁盘上的字节真的变了，而且不可撤销**。那个动作发生在上下文之外。

## 第 2 章 四个方向

```text
                ┌─── 面向模型 ────┐   决定送什么 token（context engineering）
                │                 │
 ┌── 循环 ──────┼─── 面向世界 ────┤   真的执行 + 守门（副作用、权限、沙箱）
 │  agent 的本体 │                 │
                └─── 面向人 ──────┘   界面、插话、中断、导航
```

### 2.1 循环不属于任何一面

它是把各面缝起来的那根线，也是 agent 之所以是 agent 的原因：

```text
只有面向模型         → 一次问答，聊天机器人
+ 面向世界           → 能查能改，但一次只干一件事
+ 循环               → ★ agent：自己决定下一步、自己纠错、自己推进
```

**去掉循环，前两面都还在，但它不是 agent 了。** 所以循环不是"三个功能之一"，是把功能变成 agent 的那个东西。

### 2.2 边界怎么划

两个最容易搞错的地方：

**① context engineering 是 harness 的子集，不是并列概念。**

判据不是"哪个模块"，而是**"这段代码在不在决定送什么 token 进去"**。同一个扩展系统：加载机制不是，改系统提示词的钩子就是。

**② 一次工具调用横跨三个地带。**

```text
① 工具定义进上下文            ← 面向模型
② 模型吐出 toolCall           ← 模型
③ 查表、决定串行还是并行       ← 循环 / 调度
④ 真的跑命令、真的写文件       ← 面向世界（不可撤销）
⑤ 结果回上下文（截断、序列化） ← 面向模型
```

**所以不能说"工具调用属于哪一面"——它是一条穿过整个 harness 的路径。**

## 第 3 章 面向模型：六问

### 问 1　对话历史怎么存？

**问题**：一次会话产生的消息，用什么结构保存？

| 选择 | 代价 / 收益 |
|---|---|
| **线性数组 + 可变** | 实现最简单；但无法回溯、无法分支、编辑会丢历史 |
| **线性数组 + 只追加** | 可回溯；但"回到某一步再走另一条路"要靠复制 |
| **树 + 只追加** | 天然支持分支、回溯、多路探索；索引与路径计算变复杂 |

**pi 的答案**：树 + 只追加。每条记录带 `parentId`，一个 `leafId` 指针标记"当前在哪"。**分支 = 移动指针**，不删除任何东西；`.jsonl` 只追加，从不改写。

**由此逼出的后续设计**：既然是树，"当前上下文"就得从叶节点沿父链回溯算出来；既然只追加，就需要一套投影规则决定哪些记录进上下文（见问 2）；既然能分支，离开一条分支时就需要摘要（否则那段工作对新路径不可见）。

**判据**：**用户会不会需要"回到刚才那一步试试别的"。** 会，就值得上树；不会，线性数组省下的复杂度是实打实的。

> 具体实现见 01 篇。

### 问 2　上下文怎么从历史算出来？

**问题**：存下来的记录，和发给模型的消息，是同一个东西吗？

| 选择 | 后果 |
|---|---|
| **是同一个** | 简单；但"存了但不发"（本地命令记录）和"发了但没存"（临时注入）都做不到 |
| **分成两层** | 存储记录事实，投影决定告诉模型什么；两层各自演化 |

**pi 的答案**：分层。**事实层**（会话树）记录发生了什么，**投影层**（`Context`）决定告诉模型什么。中间是一套投影函数：按位置裁剪（哪一段进）、按类型转换（每种记录怎么变成消息）。

**这个分层带来的能力**：某条记录可以只显示不发送；某种记录可以在投影时被重建成别的形态；压缩可以把一整段替换成摘要而原始记录仍在树上。

**判据**：**有没有"记录了但不该给模型看"或"要给模型看但不值得记录"的东西。** 只要有一个，就值得分层。

> 具体实现见 02 篇。**"事实层 vs 投影层"是本系列最通用的一个心智模型。**

### 问 3　一次请求带什么？

**问题**：第 N 轮的请求里，放全部历史还是只放增量？

| 选择 | 前提 |
|---|---|
| **全量重发** | 需要提示词缓存，否则成本平方增长 |
| **增量 + 服务端会话** | 需要 provider 支持有状态会话；跨 provider 难移植 |

**pi 的答案**：每轮重发全部历史。

**这个选择的支撑点是缓存**——不是可选优化，是**这个架构能跑起来的前提**。一个 80k token 的会话每轮全价重发，没人用得起。

**由此逼出的后续设计**：既然靠缓存，那么"改动落在第几个 token"就变成了工程约束（见问 5）。

**判据**：**目标 provider 有没有前缀缓存。** 没有，全量重发就是灾难；有，它换来的是无状态、可移植、易调试。

> 具体实现见 03 篇。

### 问 4　上下文满了怎么办？

**问题**：历史无限增长，窗口有限，冲突时怎么办？

| 选择 | 后果 |
|---|---|
| **直接报错** | 最诚实，但用户体验断崖 |
| **截断最老的** | 简单；但丢失的是最初的目标和约束，往往最重要 |
| **有损摘要** | 保住要点；但需要一次额外的 LLM 调用，且信息真的会丢 |
| **外置检索** | 历史存向量库，按需取回；架构复杂度大幅上升 |

**pi 的答案**：有损摘要。把老的一段交给模型总结成一份**结构化交接文档**（目标 / 约束 / 进度 / 决策 / 下一步 / 关键上下文），用摘要替换那一段。

**三个衍生问题，每个都有独立答案：**

```text
什么时候压？   按剩余量而非百分比 —— 防的是"下一次回答写不下"，那是绝对量
压到哪里？     保留最近一段原文；切点不能落在破坏协议的位置
什么信息豁免？ ★ 见下
```

**"什么信息豁免于有损压缩"是这一问里最值得学的部分。** pi 把"读过/改过哪些文件"单独抽出来，**不交给 LLM 摘要**，而是结构化提取、跨压缩累加、以精确列表形式附在摘要末尾。

理由：摘要说"助手查看了一些配置文件并做了修改"是可接受的损失；但**文件路径记错，模型下一轮就会去改错文件**。

**判据**：**哪些信息一旦失真就会导致错误动作。** 那些必须走独立通道，用代码保证，而不是写进提示词请求模型"务必保留"——**"要求"不等于"保证"。**

> 具体实现见 06 篇。

### 问 5　成本怎么控？

**问题**：token 要花钱，怎么少花？

前缀缓存把"提示词的排布顺序"变成了工程约束：

```text
缓存按前缀逐字节匹配
   → 第 N 个 token 处发生改动
   → 第 N 个 token 之后的全部缓存失效
```

**于是同样大小的改动，代价差几个数量级，只取决于位置。** 一个 200 token 的新工具定义，若插在最前面的工具区，可以废掉后面 80k token 的缓存。

**pi 的答案**是三条手法：

```text
① 稳定的在前，易变的在后    排布顺序 = 变化频率的倒序
② 不缩小改动，改而移动改动   把新增内容渲染到缓存断点之后
③ 优化前提不成立就退回全量   静默退回，不报错，只是少省一点
```

第三条在 pi 的这条链路上出现了三次，**是缓存类设计的通用底线：缓存失效只是变贵，缓存用错是直接出错。**

**判据**：**这个系统会不会在会话中途改变靠前的内容**（工具集变化、系统提示词变化）。会，就值得为"把改动挪到后面"付出复杂度；不会，这套机制什么都不做。

> 具体实现见 05 篇。

### 问 6　提示词分几层、谁能改？

**问题**：系统提示词是一个字符串，还是一个可组合的结构？

| 选择 | 后果 |
|---|---|
| **一个字符串** | 简单；但扩展想加一句就得字符串拼接，且改动会累积 |
| **底稿 + 覆盖层** | 底稿按料变化时重建，覆盖层每轮清零；两个变化源互不干扰 |

**pi 的答案**：分两层，取用时才合成（`override ?? base`）。底稿在"工具集或资源变化"时重建，覆盖层由扩展每轮改写、每轮清空。

**为什么必须是两个字段而不是一个**：一轮进行中工具集若发生变化，底稿必须重建，**但扩展这一轮的改写不能被冲掉**。合成一个字段就再也分不开了。

还有一条边界值得记：**可替换的是"主张"，不可绕过的是"事实"。** 用户可以整个替换掉 agent 的人格与指令，但项目约定文件、可用技能清单、工作目录这些**客观事实**照常追加——"我想换个人格"和"我想让模型不知道项目里有约定文件"是两回事。

**判据**：**有几个独立的变化源。** 一个就用一层；两个以上就分层存储、取用时合成，**别提前压平**。

> 具体实现见 05 篇。

## 第 4 章 面向世界：四问

### 问 7　工具怎么声明给模型？

| 选择 | 可靠性 |
|---|---|
| **提示词内嵌**（`toolname: description` + 输出格式约定） | 低；靠正则解析模型的文本输出，格式常跑偏 |
| **API 原生 function calling** | 高；模型输出结构化块，可加 schema 约束 |

**pi 的答案**：完全依赖原生 function calling，没有任何降级路径。

**一个常见的误解值得澄清**：原生 function calling 不是"模型凭空知道"。服务端仍然把工具定义**渲染进模型的 token 流**，只是用了模型训练过的固定格式。**它比手写更可靠，不是因为机制更高级，而是因为格式约定被固化进了权重里。**

**推论**：工具照样占 token、照样在缓存前缀里、照样和消息抢注意力。"工具太多导致模型选错"不是玄学。

**判据**：**目标 provider 支不支持。** 支持就别自己造；不支持（本地小模型、老端点）就只能内嵌，并接受解析不稳定的代价。

> 具体实现见 05 篇。

### 问 8　工具怎么调度？

**问题**：模型一次点名调三个工具，怎么执行？

| 选择 | 代价 |
|---|---|
| **全串行** | 简单、可预测；慢 |
| **全并行** | 快；但有副作用冲突风险，且结果顺序不确定 |
| **按工具声明分** | 工具自己说能不能并行 |

**pi 的答案**：第三种，且**一批里只要有一个声明"我不能并行"，整批退回串行**。

**这个保守选择的理由**：安全的并行子集难以判定时，**放弃优化比划错代价小**。并行执行还额外要求"结果顺序等于输入顺序"——上下文必须可重放，不能受网络快慢影响。

**判据**：**工具会不会互相干扰。** 只读工具随便并行；碰同一份状态的必须串行。

> 具体实现见 03 篇。

### 问 9　副作用怎么守门？

**问题**：模型说要执行 `rm -rf /`，谁来拦？

| 选择 | 适用场景 |
|---|---|
| **不拦** | 单人本地、用户本来就有 shell |
| **每次审批** | 用户不完全信任模型，或操作不可撤销 |
| **白名单 / 路径限制** | 半自动，规则可预先声明 |
| **沙箱隔离** | 多租户、不可信代码、云端执行 |

**pi 的答案**：**基本不拦，但留钩子。** 只有一次性的文件夹级信任提示（决定要不要加载这个项目的配置和扩展），以及一个可以拦截任意工具调用并拒绝它的扩展钩子。

**这是"提供机制，不提供策略"的典型**，直接来自 pi 的核心哲学：能做成扩展的就不进核心。

**判据**：**执行环境和信任模型。** 跑在用户自己机器上、用户自己的项目里、用户看着——审批的边际价值很低（他本来就能自己跑那条命令）。换成云端多租户，沙箱立刻从"可选"变成"必须"。

**这一问是四方向里差异最大的一块**，也是 pi 教不了你的部分。

### 问 10　错误怎么表达？

**问题**：工具执行失败了、参数非法了、被拦截了，怎么表达？

| 选择 | 后果 |
|---|---|
| **抛异常给人** | 中断流程，人来处理 |
| **折成数据给模型** | 变成一条结果消息回到对话，模型自己纠正 |

**pi 的答案**：**默认折成数据**。工具不存在、参数非法、被扩展拦截、执行超时——统统变成一条错误结果消息回到上下文，模型下一轮读到后自行调整。

**但不是所有错误都能这么办。** 摘要生成失败就只能抛：没有摘要就无法压缩，无法压缩就无法继续——**这不是模型能处理的问题**。

**判据**：**模型能不能据此做出更好的下一步。** 能，就折成数据（这也让 agent 有了自我纠错能力）；不能，就抛给人。

**同一个系统里两种都要有，混用不是不一致，是按问题性质分类。**

> 具体实现见 03 篇、06 篇。

## 第 5 章 面向人：两问

### 问 11　人怎么介入正在跑的 agent？

**问题**：模型正在生成、工具正在执行，用户想说句话或喊停，怎么办？

| 能力 | 难点 |
|---|---|
| **中断** | 信号要能传到最深处（HTTP 流、子进程），且检查点位置决定了状态是否一致 |
| **插话** | 注入点必须在"下一次请求发出之前"，否则要么被忽略要么打断当前轮 |
| **导航** | 跳到历史某点继续——依赖问 1 的存储结构 |

**pi 的答案**：三样都做。中断信号一路往下传；插话进队列，在每轮请求发出前取；导航靠移动树指针。

**中断这一问里最值得学的是检查点的位置。** pi 在压缩流程里把中断检查卡在"摘要已生成、尚未落盘"之间：

```text
生成到一半被中断 → 摘要可能不完整 → 绝不落盘 → 历史纹丝未动
```

**要么完整完成并落盘，要么什么都没发生。原子性不是靠事务，是靠检查点放在哪。**

**判据**：**有没有人在实时看着。** 无人值守的流水线 agent，这一整块可以是零。

> 具体实现见 `generated/modes-and-tui`、03 篇、06 篇。

### 问 12　同一个核心怎么服务多种前端？

**问题**：交互式终端、一次性命令行、被别的程序嵌入——三种用法差异极大。

| 选择 | 后果 |
|---|---|
| **各做一套** | 行为容易漂移 |
| **核心 + 前端适配** | 需要找到那个接缝在哪 |

**pi 的答案**：一个核心，三个前端。**接缝是"需要人做决定"的地方**——比如"要不要信任这个项目"这种问题，交互式弹窗、协议转发给宿主、静默返回默认值，三种实现同一个接口。

**这个接缝的位置很有启发**：三种前端的差异，本质上全部集中在"遇到需要人决定的事怎么办"。找到它，核心就能保持单一。

**判据**：**会不会有第二种使用方式。** 会，就提前把"需要人决定"的地方抽成接口。

> 具体实现见 `generated/modes-and-tui`。

## 第 6 章 循环：三问

### 问 13　"一轮"的边界是什么？

**问题**：`while` 循环转一圈，算一轮什么？

**这是最容易糊的地方，因为"一轮"在不同层次指不同的事。** pi 有四层嵌套：

```text
一个用户回合  ⊇  一次 agent run  ⊇  一个 turn  ⊇  一次请求  ⊇  一个 SSE 事件
     │              │                  │
     │              │                  └ 一次请求 + 它的工具执行
     │              └ 从 prompt 到 agent_end 之间，一次完整的 agent 运行
     └ 从用户输入到界面回到可输入，中间可能跑好几次 run（重试 / 压缩 / 补刀）
```

**从上往下，每一层的"一次"都可能对应下一层的多次。**

**这个区分为什么重要**：任何"什么时候能做 X"的问题，答案都是某一层的边界。比如压缩发生在"一个回合内、两次 run 之间"——**不是"两个 turn 之间"**，差别很大。

**判据**：**每引入一层循环，就要能说清它的退出条件和它管什么。** 说不清就是层次划错了。

> 具体实现见 03 篇、06 篇。

### 问 14　状态放在哪一层？谁拿引用谁拿快照？

**问题**：消息列表、工具集、模型选择这些状态，谁持有真相？

**pi 的答案**是三层，且**跨层时拷贝**：

```text
会话树（文件 + 索引）    永久、只增不删、树状
      ↓ 投影
state.messages          线性数组、跨 run 存活
      ↓ ★ 拷贝（.slice()）
currentContext.messages 局部变量、run 结束就没了
```

**"跨层拷贝"这个决定，后果比看上去大得多。**

循环拿到的是快照，一次 run 从头到尾用同一份，**中途不回头看上层**。于是：

```text
想改历史（压缩）→ 循环手里的副本不会跟着变
                → 必须结束这次 run、改完、重开一次 run 重新拷快照
```

**"压缩必须在循环外"不是设计偏好，是快照语义的必然结果。**

**判据**：**下层执行期间，上层状态会不会变。** 会变而又用引用，就会出现"执行到一半世界变了"的竞态；用快照则代价是改动要等下一次才生效——**通常后者更好，因为"一次执行内世界是静止的"极大简化推理。**

> 具体实现见 06 篇第 1 章。

### 问 15　什么时候允许改写历史？

**问题**：agent 运行期间，能不能修改已经发生的记录？

**pi 的答案**：只有压缩会改写历史，而且**只在两次 run 之间**。

其余时刻，历史只增不删。这条约束换来的是：**任何一次 run 内，历史是静止的**——不用考虑"我读到一半有人改了它"。

**更值得注意的是"改写"的实际做法**：不是真的删除，而是**在树上追加一条压缩记录**，投影时用摘要替代被覆盖的那一段。**原始记录永远还在。**

```text
物理上：只追加，从不删除
逻辑上：投影规则决定哪些还算数
```

**判据**：**"撤销"和"审计"要不要支持。** 要，就只能追加、靠投影表达变更；不要，原地修改省事得多。

> 具体实现见 01 篇、06 篇。

## 第 7 章 用法：量四块的重量

四个方向不是"都要做满"，而是**按场景分配重量**。看任何 harness，先问三句话：

```text
① 它把重量压在哪几块？
② 不做的那几块，是场景不需要，还是留给上层？
③ 留了钩子还是干脆没有？
```

几种典型分布：

| 系统类型 | 模型侧 | 世界侧 | 人侧 | 循环 |
|---|---|---|---|---|
| **单人本地 CLI**（pi） | 极重 | **极轻**（只有钩子） | 很重 | 朴素 |
| **带权限系统的编码助手** | 重 | **重**（每次审批） | 重 | 朴素 |
| **云端多租户平台** | 重 | **重**（沙箱、配额） | 轻 | **重**（编排、子 agent） |
| **流水线 / 无人值守** | 重 | 中 | **≈ 0** | 中 |

**重量分布由使用场景决定，不是谁做得更全。**

pi 世界侧极轻不是缺陷——它跑在你自己机器、你自己项目里，你本来就有 shell，审批的边际价值很低。同一套做法搬到云端多租户就是灾难。

### 7.1 一个诊断技巧

**看一个 harness 最快的方法：找它的"最难的那一块"在哪。**

pi 最难的部分是会话树、压缩、缓存前缀——全在模型侧。所以读 pi 的源码，你会觉得 agent 就是 context engineering。

**这个感觉准确反映了 pi 的重量分布，但不是 harness 的固有形状。** 换一个权限系统完整的实现，"每次工具调用要不要放行"会立刻变成最重的一块。

## 第 8 章 带走的清单

不看正文，能对一个陌生的 harness 答出这些，就算看懂了它：

**面向模型**
1. 历史怎么存？树还是线性？可变还是只追加？
2. 存储和上下文是不是同一个东西？有没有投影层？
3. 每轮带全量还是增量？靠什么支撑这个选择？
4. 上下文满了怎么办？什么信息豁免于有损压缩？
5. 缓存前缀怎么保？中途改变靠前内容时怎么办？
6. 提示词分几层？谁能改？哪些不可绕过？

**面向世界**

7. 工具怎么声明？原生还是内嵌？
8. 一批工具怎么调度？谁决定串还是并？
9. 副作用怎么守门？提供机制还是提供策略？
10. 错误折成数据还是抛给人？分界在哪？

**面向人**

11. 能不能中断？中断检查点放在哪？插话注入点在哪？
12. 支持几种前端？接缝在哪？

**循环**

13. "一轮"有几层？各自的退出条件是什么？
14. 状态在哪一层？跨层是引用还是快照？
15. 什么时候允许改写历史？物理删除还是逻辑覆盖？

### 三条最通用的心智模型

如果只带走三样，我会选这三个——**它们跟 agent 都没有必然关系，是更一般的工程判断**：

**① 事实层 vs 投影层。** 存储记录发生了什么，投影决定告诉谁什么。**分层存储、取用时合成，别提前压平**——压平了就再也拆不开。

**② 优化的前提不成立时，静默退回全量那条永远正确的路。** 不报错、不抛异常，只是少省一点。因为**优化失效只是变贵，优化用错是直接出错**。

**③ 判据不是"这东西属于哪个模块"，而是"它在回答哪个问题"。** 同一个扩展系统，加载机制不是 context engineering，改提示词的钩子就是；同一条压缩摘要，在压缩里是"活边界"，在分支摘要里是"一段历史"。
